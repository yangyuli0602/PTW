# 03 · C.01b 特殊账户程序

> 上数方式：**派生**（从 BKD 筛）+ 人工（对账单金额）
> 生成顺序：**第 3 张**，依赖 BKD 定稿
> 模板 sheet：`C.01b 特殊账户程序`

## 1. 角色

针对**其他货币资金**（微信/支付宝余额、存出投资款、保证金、票据保证金等）执行的替代程序表。
银行存款走函证（C.01），平台类账户拿不到银行回函，只能靠对账单/资产证明书核对，本表就是这套程序的载体。

两个核心判断：**账面金额对不对**（与对账单比）、**有没有受限**（受限金额 + 原因）。

## 2. 表结构（模板 V7 实测）

| 项 | 位置 |
|---|---|
| 标题 | `B2` = `C.01b 特殊账户程序`，`B6` = `重大的其他货币资金项目（如，微信支付余额、存出投资款余额等）` |
| 装饰 | `B8`（分隔线） |
| **表头行** | **第 9 行** |
| 数据区 | 第 10~12 行（**预置 3 行**） |
| 合计 | 第 14 行：`G14` = `合计`，`H14` = `=SUM(H10:H12)`，`L14` = `=SUM(L10:L12)` |
| 复核标记 | 第 15 行：`H15`/`L15` = `RX` |
| 程序说明 | `B16`（"1.可能有助于我们进行确认受限情形的程序包括…"） |
| 异常记录 | `B18`，`B19:F22` 合并为输入框 |

表头各列：

| 列 | 表头原文 | 说明 |
|---|---|---|
| B | 公司名称 | 主体 |
| C | 科目名称 | 其他货币资金 |
| D | 银行/存款机构名称 | 平台/机构名 |
| E | 账号 | 平台账号 |
| F | 币种 | 三字母代码 |
| G | 期末账面金额（原币）**A** | 原币 |
| H | 期末账面金额（本币） | 本币 |
| I | 对账单/资产证明书金额（原币）**B** | **人工填**，平台无来源 |
| J | 账面金额与银行账户余额差异 **C=B−A** | `=IF(I="","",I-G)` |
| K | 账户类型、性质和用途 | 人工/判断 |
| L | 本期末实际受限金额（本币） | 人工填，0 也要写 0 |
| M | 记录受限原因、确认受限情形进行了适当的分类和披露；记录我们的补充工作 | 人工 |

实测生成形态：数据 10~26（17 行）、合计 27（`G27`/`H27`/`L27`）、RX 28、说明 29。

## 3. 哪些行进表

**从 BKD 筛「其他货币资金」且本币金额非零的行。**

实测对照（2026-11-05）：BKD 其他货币资金 27 行 → C.01b 17 行，
剔除的 10 行全部是**本币余额为 0** 的账户，合计金额与 BKD 完全一致（235,111,731.69）。

规则：

| 情形 | 是否进 C.01b | 理由 |
|---|---|---|
| 其他货币资金，金额 ≠ 0 | **进** | 有余额就要证明其在、且不受限 |
| 其他货币资金，金额 = 0 | 不进 | BKD 里已作为完整性证据保留 |
| 银行存款 | 不进 | 走 C.01 函证 |
| 库存现金 | 不进 | 走盘点程序 |

> 表名叫"重大的其他货币资金项目"，实务上可以按金额门槛筛「重大」。
> **但本版不设金额门槛**：其他货币资金往往笔数少、性质特殊，漏一个就少一项程序。
> 如果客户其他货币资金有几百个账户，再加门槛，并把门槛值写进 `B6` 下面的说明、在待确认清单里列明。

## 4. 每个数怎么来

| 列 | 来源 | 规则 |
|---|---|---|
| B 公司名称 | BKD B 列 | 原样 |
| C 科目名称 | 固定 `其他货币资金` | — |
| D 银行/机构名 | BKD D 列 | 需解析出机构名（实测大面积等于主体名，属 C 类缺陷） |
| E 账号 | BKD E 列 | 文本格式，防前导零 |
| F 币种 | BKD F 列 | — |
| G 原币 | BKD G 列 | 原样 |
| H 本币 | BKD J 列（折算人民币） | **与 Lead 同口径**，见总则 4.5 |
| I 对账单金额 | **人工** | 未取得 → 留空标黄 `FFFF00`，不填 0 |
| J 差异 | 公式 | `=IF(I{row}="","",I{row}-G{row})` |
| K 账户类型/性质 | 人工 | 如「微信支付余额」「票据保证金」「存出投资款」 |
| L 受限金额 | 人工 | 未确认 → 留空标黄；确认不受限 → 写 0 |
| M 受限原因/补充工作 | 人工 | 有受限才写 |

### J 列为什么必须判空

模板原公式是 `=I10-G10`。I 列空时，Excel 把空当 0，算出「差异 = −账面」，
一眼看过去像是核对出一个巨额差异——**假差异比真差异更危险**。
必须用 `=IF(I="","",I-G)`，并且第 9 行表头写的是 `C=B−A`，两者一致。

### 差异按原币比，不按本币

A 列是原币（G）、B 列也是原币（I），所以 C = B − A 是原币差异。
本币差异只在 L 列（受限金额）里出现，两者不要混。

## 5. 合计与校验

| 项 | 公式 |
|---|---|
| 原币合计 | `G{s} = SUM(G{ds}:G{de})` |
| 本币合计 | `H{s} = SUM(H{ds}:H{de})` |
| 受限合计 | `L{s} = SUM(L{ds}:L{de})` |

```text
H 合计 == BKD 其他货币资金合计（本版 235,111,731.69）
       == Lead 其他货币资金期末账面数（F39）        ← 三条口径必须闭合
J 列：I 有值才出数，I 空则空（不得为 -账面）
L 合计 ≤ H 合计（受限金额不可能超过余额）
所有 I 列为空的行，已进入"待人工取对账单"清单
```

> 若客户存在「已单独列示的受限/保证金」在 Lead 里重分类过，则：
> `C.01b 合计 == BKD 其他货币资金 − 已单独列示部分`，差额必须能解释到具体账户。

## 6. 格式要求

- 表头行高与模板一致，自动换行；数据行高 14.7；
- 金额 `#,##0.00`，账号 `@`；
- I / K / L / M 列（人工列）保持模板底纹，**不要覆盖模板的颜色规则**；
- 数据区扩行时，样式、列宽、合并区、条件格式必须跟着扩（不许出现"新行是裸格"）。

## 7. 已知坑

1. **插行不搬合并区**：这张表 `B19:F22` 是异常记录输入框，扩数据区时若直接插行，
   输入框会被压进数据区。用"保留版面"的插行方式。
2. **预置行数会变**：模板 3 行，实测扩到 17 行。合计行位置必须按"数据末行 + 1"现算。
3. **D 列银行名等于主体名**：平台账户（微信/支付宝）本身没有"银行"，写主体名会让读者以为没填。
   识别不出就留空标黄，或写平台名（如「支付宝」），不要填主体名。
4. **账号带后缀**：实测存在 `1817320828`（银行存款）与 `1817320828-1`（其他货币资金）两个不同账号，
   后者是 TB 里真实存在的独立账号，不是程序臆造。**比对时按完整字符串，不要截断。**
5. **受限金额为 0 与留空不是一回事**：0 = 已确认不受限；留空 = 还没确认。混起来就失去了程序证据。

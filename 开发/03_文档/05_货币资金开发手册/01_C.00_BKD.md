# 01 · C.00 BKD（全量货币资金明细表）

> 上数方式：**原始录入**（TB 直取，一行一个账户）
> 生成顺序：**第 1 张**，其余四张表都以本表为数据源
> 模板：`data/bkd_tpl/C SWP 货币资金 模板 V7.xlsx` / sheet `C.00 BKD`

## 1. 角色与边界

BKD 是货币资金底稿的**唯一明细源**。它要证明两件事：

1. **完整性**：本期所有货币资金账户都在表里（含 0 余额、本年销户、上年有本年无）；
2. **准确性**：每行本币金额能加总到余额表的货币资金合计。

后续四张表全部从它取数：Lead 做科目汇总、C.01b 挑平台账户、C.02a 按币种折算、C.03 定测试账户范围。
**所以 BKD 的行与金额一旦定稿，后面四张表的引用区间一次性锁定。**

### 2.2 生成后形态（插 2 列后）

**折算两列插在 H（期末账面金额本币）之后**，成为新的 I、J 列；模板原有的 I~L（性质用途、
是否函证、判断理由、Notes）整体右移为 K~N。

> 为什么不放到最右（Notes 之后）：折算率是"原币 → 人民币"的桥梁，必须紧邻原币列与本币列，
> 复核人一眼能看出 `原币 × 汇率 = 人民币`。放到最右，中间隔着四列，读起来要来回跳。
>
> **注意**：`_参考_货币资金口径.md` 原写「折算列接在模板已用列最右，绝不插进模板中间」，
> 与实测实现（插在 H 之后）不一致。**以实现为准**，回头把那句改成
> 「折算两列紧接本币列之后（不插在原币与本币之间），原有列整体右移」。
> 「绝不插进中间」的真实含义是：**不许插在原币（G）与本币（H）之间**，那会把一对金额列劈开。

## 3. 行怎么来

### 3.1 取数

- 从 TB 表中筛 `acct_l1 ∈ {库存现金, 银行存款, 其他货币资金}`（匹配规则见总则 4.1）；
- **一个账户一行**。账户键 = 主体 + 一级科目 + 账号 + 币种；
- 无账号的（库存现金、部分其他货币资金）按**币种拆行**：USD/EUR/HKD/CNY 各一行，金额为 0 也保留。
  实测库存现金就是 4 行（USD 0 / EUR 0 / HKD 480 / CNY 0，本币 416.90）。

### 3.2 必须保留的行（完整性证据）

| 情形 | 处理 |
|---|---|
| 期末余额为 0 | **保留**，Notes 写「期末余额为零」 |
| 本年销户 | **保留**，Notes 写销户日期/说明 |
| 上年有、本年无 | **保留**，金额填 0，Notes 写「上年有本年无，需确认是否销户/漏记」 |

这三类是审计证据，不是冗余数据。删掉就无法证明"该有的账户都包含了"。

### 3.3 上年回捞

- 上年同账户的账号、银行名称、Notes 用「科目 + 银行」或「账号」回捞；
- **回捞不到就留空，绝不生成新编号**（曾出现把 `1817320828` 编成 `1817320828-1` 的臆造嫌疑，
  实测该账号在 TB 中真实存在，属误判——但"不臆造"的原则不变：号码只能来自 TB 或上年底稿）；
- 上年 BKD 底稿未提供时，全部行按「本年新增」处理并逐行标注，不得当成"已核对一致"。

## 4. 每列的写入规则

### B 公司名称
TB `company_name`；为空退 `book_name`。**不做主体过滤**（见总则 4.4）。

### C 科目名称
写一级科目全称，只用三个值之一：`库存现金` / `银行存款` / `其他货币资金`。
后续 Lead 的 SUMIF 就按这三个值匹配，**改名会导致 Lead 打空**。

### D 银行/存款机构名称

**照抄「辅助核算项1」（`aux1`）原值，不做任何解析改写。** `aux1` 空时依次退 `aux2` / `aux3` / `aux_text`。

这一列在真实底稿里就是客户系统辅助核算的值：可能是主体全称、可能是「主体-开户行」、
也可能是「保证金账户」。**程序不许把它规范化成标准行名**（汇丰银行 / 花旗银行 之类）：

- 客户资料上写的是「Hai Robotics Europe B.V.」，底稿却写「汇丰银行」，
  复核时按辅助核算回查会**对不上**；
- IBAN 里那 4 位银行代码只在账户本身是 IBAN 时才存在，国内户是裸账号，解析必然空一片，
  最后还是要人工补，白白多一道「程序改了一半」的工序。

> 走过一次弯路，记在这里免得再犯：曾按「IBAN 银行代码 → 中文行名」解析过一版，
> 海外 10 户确实变成了「汇丰银行 / 花旗银行」，但国内 151 户全空、并与客户辅助核算值脱节。
> 业务口径是**原值照抄**，「看起来更规范」不等于「更对」。

**库存现金**：没有开户行和账号，D、E 两列填 `/`（不适用），不填 `—`、也不留空。
`/` 是审计底稿里"该有内容但业务上确实没有"的通用写法。

> 三列同一条边界：**该有内容、但业务上确实没有 → `/`**；
> **还没查到/还没判断 → 留空 + 标黄 + 进待补清单**。两者不能混。

### E 账号1
TB `bank_account` 原样写入，**单元格数字格式设 `@`（文本）**，防前导零丢失（如 `000441582864`）。
无账号的按上一条填 `/`。

### F 币种
统一成三字母代码：`CNY` / `USD` / `EUR` / `HKD` / `JPY` / `SGD` / `AUD` / `GBP` / `KRW`。
TB 里是「美元(USD)」这类中文+括号形式，需要归一。
**外币行的币种取自外币原币行，不是综合本位币行**（综合本位币行 `currency='综合本位币'`，不能当币种用）。

### G 期末账面金额（原币）
外币原币行的期末原币余额（`end_bal_fx`，或 `end_debit_fx − end_credit_fx`）。
人民币账户原币 = 本币。

### H 期末账面金额（本币）
**只取综合本位币行**的 `end_debit − end_credit`。格式 `#,##0.00`。

### I 折算率
人工列，默认 `1`，**标黄 `FFFF00`**。平台无汇率源，汇率由项目组填。
外币账户的折算率空着或填 1 都是错的，必须提醒人工。

### J 期末账面金额（人民币）
`=IF(H{row}="","",ROUND(H{row}*I{row},2))`

- **Lead 的 SUMIF、BKD 自己的合计勾稽全部走这一列**，不走 H 列；
- 外币主体拿本币去勾稽必现假差异，那是口径不同不是错——所以统一走 J。

### K 货币资金账户的性质和用途
人工/后续 AI 判断。**库存现金填 `/`**（没有"用途"可填），其余科目留空等人填。

### L 是否对账户执行银行函证程序？
- **银行存款恒填 `是`**，不标黄（规则性动作，机器可判）；
- **库存现金填 `/`**：现金没法向第三方函证，这一列对它不适用；
- 其他货币资金：按金额与性质判断，判断不了就留空标黄；
- 该列有数据验证（列表 `是,否`），写入值必须精确等于 `是` 或 `否`，否则验证报错。

> 库存现金行写了 `/` 之后，点进该格时下拉列表里没有这个选项（验证是 `是,否`）。
> 程序写入不触发验证，不影响生成；只是若要手工改成别的值，得先清除验证。
> 这一列对现金本来就不该改，暂不为它放宽验证。

### M 判断理由
`=IF(L{row}="是","N/a","")` —— 走折算率列插入后位置右移，公式里的 `L{row}` 要跟着改。

**库存现金例外**：直接写常量 `/`，不留公式。
公式在 L 不等于"是"时会算出空字符串，看上去跟"还没填"一样；
而现金这一列本来就是"不适用"，得让人一眼看见。

> 三列同一条逻辑：**该有内容、但业务上确实没有 → `/`**；
> **还没查到/还没判断 → 留空 + 标黄 + 进待补清单**。两者不能混，
> 混了之后"待补清单"里会混进一堆根本不需要补的行，真正要补的反而被淹掉。

### N Notes
自由文本，写：0 余额、销户、上年有本年无、账户性质特殊说明、外币账户汇率待填等。

## 5. 合计与勾稽

| 项 | 公式 | 校验含义 |
|---|---|---|
| 合计（本币） | `=SUM(H{dataStart}:{dataEnd})` | 与 Lead F41 相等 |
| 合计（人民币） | `=SUM(J{dataStart}:{dataEnd})` | 与 Lead F41 相等（Lead 取 J） |
| 复核标记 | `RX` | 人工复核位 |
| 勾稽 | `J{s} - 'C.00 Lead'!F41` | 必须为 0 |

**勾稽必须用 J 列（折算人民币）**，不是 H 列。外币主体下 H 列勾稽必然不平。

## 6. 格式要求

- 表头行高 43.9、自动换行；数据行高 14.7；
- 金额列 `#,##0.00`；账号列文本 `@`；日期 `yyyy-mm-dd`；
- 边框：数据区四边细线，合计行上边框；表头无底纹（颜色由模板给，不要新造）；
- 条件格式 `B10:K15` 需随数据区扩张到实际末行（否则新增行没有格式）；
- 插入的两列要同步设列宽（16.5 与相邻列一致）。

### 6.1 新增列的表头一律走「格式刷」逻辑

**规则：不许给新表头单独拼样式，一律调用 `_style_header_like()`。**

它做的事：整格照抄左邻（找不到就右邻）的 font / fill / border / alignment / number_format，
再强制 `wrap_text=True`，只改文字和列宽。

为什么必须这样（V1.2.38 修的真实 bug）：

```python
cell.alignment = _BKD_ALIGN_C      # ← 错：整体替换对齐对象，邻居带来的 wrap_text 一起没了
```

表现很隐蔽——同一行表头里，字体、加粗、底色、边框全都对，**唯独新增的两格不换行**，
其他格都折成两行。看图只会觉得"这两列挤"，很难想到是代码把 alignment 覆盖了。

表头文字本身也要与邻居同构：`期末账面金额` / 换行 / `（人民币）`，
不要写成一整行让列宽去断（列宽 18 会断在「人」字上）。

配套断言：`tmp/test_fx.py` 里有「新增表头都自动换行」一条，新增列若再丢 wrap 会直接测试失败。

## 7. 校验

```text
Σ H(数据区)  == Lead F41
Σ J(数据区)  == Lead F41
行数 > 0，且三个科目都出现（某科目本期确实无余额 → 要有 0 金额行，不是整类消失）
E 列为文本格式，无科学计数法、无前导零丢失
D 列无「等于主体名」的值（实测缺陷项）
L 列取值 ⊆ {是, 否, 空}
```

## 8. 已知坑

1. **SUMIF 区间写死**：Lead 引用 `$C$10:$C$201`、C.01b/C.02a 引用 `$F$10:$F$201`。
   BKD 行数一变，这些区间必须同步，否则金额打空且程序仍报成功。
2. **插列顺序**：必须先解合并再插列，否则模板 `B22:F24`（Notes 输入框）会被清成空白且丢样式。
3. **合计行位置随行数变**：模板在 17 行，192 行数据时在 203 行。一律按"数据末行的下一行"现找。
4. **库存现金拆多行不算重复**：4 个币种 4 行，但合计只等于综合本位币的 416.90，不会翻倍。
5. **`—` 与空值不是一回事**：无账号写 `—`（模板样式），解析和 SUMIF 时要跳过 `—`。

## 3. 开发内容（5 个阶段）

### P0 · 数据准备（前置，约 2 小时）

1. 平台导入脱敏 TB（**必须保留核算维度列**，映射到 `aux1=核算维度编码`、`aux2=核算维度名称`）

## 4. 标黄与「待确认清单」的规则（这是本次的核心体验）

**标黄只表示一件事：这个格子需要的资料没拿到。** 不代表错误，也不代表 0。

| 情形 | 处理 |
|---|---|
| 有数据源、值为 0 | 正常写 0，**不标黄**（零余额账户必须保留） |
| 有数据源、算出空 | 标黄 + 原因「源表该列为空」 |
| 根本没有数据源（性质、是否函证、上期数） | 标黄 + 原因「需人工判断/无上年资料」 |
| 需要人力判断的结论（受限、无调节项） | 本次不涉及（属 C 级，见备忘 §7.5） |

清单四项，导出的 Excel 和页面都可见：

1. **待补**：缺账号/银行名（附主体+科目+金额）
2. **待判**：性质、是否函证（附建议值，标注"建议"）
3. **无源**：上期审定数、账表调整数
4. **未勾稽**：说明原因，不假装对上了

## 6. 风险与已知限制（**测试时要盯着这几条**）

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | 序时账单文件 **1,000,001 行**（整百万） | 高度疑似导出截断，费用总额可能偏小 | 生成时在检查表**红字提示**；不假装完整 |
| 2 | 脱敏账号是 `账号010` 这种假号 | 不能用于函证 | 输出文件名与页面都标注「数据已脱敏，账号仅供流程验证」 |
| 3 | TB 期间 1–6，序时账到 7 月 | 若不过滤期间，费用会多算 7 月 | 默认 `period_to=6`，可改；过滤后行数在页面显示 |
| 4 | 上期数全缺 | K 列、变动率、是否进一步调查全部无法算 | 标黄，不填 0 |
| 5 | `openpyxl` 另存可能丢模板部件 | 底部隐藏 sheet / x14 下拉损坏 | 保存前后比对 `zip` 部件清单，缺了立即报错 |
| 6 | 费用模板只有 3 个数据位 | 96 个科目要插 90+ 行 | 插行后必须重写 `SUM(E29:E33)` 等区间，并平移合并单元格 |
| 7 | 主体 mapping 表有带/不带 `(101)` 两种写法 | 直接精确匹配会漏 | 两级匹配（精确 → 归一），未命中进清单 |

## 7. 验收标准（交给别人测试时照这个走）

**准备**：平台导入脱敏 TB + 3 个序时账文件 → 清洗 → 映射（含核算维度）→ 合并。

**测银行存款**：

1. 进「三、底稿生成」→「银行存款底稿」→ 预览 → 应显示 **124 行**
2. 生成 → 下载 Excel → 打开 `C.00 BKD`
3. 核对：明细行数 124；H 列合计 = TB 里 1001+1002+1012 期末本位币借合计（排除综合本位币行）
4. 核对：I/J/K 列**全部是黄色**且有批注说明
5. 核对：银行名 ≥123 个非空、账号 ≥123 个非空，且账号是**文本格式**（左对齐、无科学计数）
6. 检查表里能看「待补 / 待判 / 无源」三类清单

**测费用**：

1. 切「费用底稿」→ 预览 → 应显示 VC、VD 两张表的科目数与行数
2. 生成 → 打开 `VC.00 销售费用BKD` → E 列每行有数、E34 合计合理
3. K 列（上期审定数）**全黄**，L/M/N 列留空
4. 插行后合计公式区间正确（不是还在 `E29:E33`）
5. `Uexp.00 Lead` 的 C4 若为空 → 页面有提示，且模板里没有被偷偷填 0

**必过项（不过就是 bug，不是数据问题）**：

- [ ] 生成两次，输出逐格一致
- [ ] 模板其余 sheet 未被改动（部件哈希一致）
- [ ] 无 `#REF!` / `#NAME?`
- [ ] **一个数字都没有被调平过**（差额要么有说明，要么标黄）

## 8. 已拍板的决策（2026-11-03 确认）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 版本号 | **V1.2.01**。清洗收口另作 V1.2.02，两条线不混 |
| 2 | 费用 BKD 的「账套」列 | **填公司名**（`10I公司` → `I公司`），与 Lead 汇总口径一致；**原始账簿名保留**——写进检查表的「账簿↔公司映射」小节，并保留 mapping 表文件不删 |
| 3 | 银行存款 I/J/K（性质/函证/理由） | **不给建议值，只标黄**。这三项属 C 级人工判断，给了值就会被人直接采用 |

> 决策 2 的落法：B 列写公司名；检查表新增「账套映射」清单（账簿全名 / 公司名 / 是否归一匹配 / 命中方式），
> 未命中的行同时在 B 列标黄。这样既能按公司口径汇总，又不会丢掉账簿这一层可追溯性。
>
> 决策 3 的落法：三列一律黄底 + 批注写「需人工判断（无上年 BKD 可回捞）」，**不写任何默认字符串**。

### 10.3 过程中踩到并已修的 5 个坑（都会在真实数据上重演）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | **「综合本位币」行重复计本币** | 金额正好翻倍（14.2 亿 → 28.4 亿） | SQL 排除 `currency LIKE '%综合本位币%'`，一个币种一行 |
| 2 | **「核算维度=合计」汇总行** | 同科目金额再翻倍 | SQL 排除 `aux ∈ (合计/小计/总计)` |
| 3 | **合并方案层「多账簿(01)」当主体** | 多出 21 个假主体 | 主体名含「多账簿/合并方案/汇总」整行跳过 |
| 4 | **主体名带 `(100)` 后缀** | 同一家公司被拆成两个主体 | 主体名归一，去尾部编码 |
| 5 | **月末「结转本期损益」冲平费用** | 每个费用科目都算成 0 | 取「借方 − （贷方 − 结转类贷方）」，结转不算费用 |

> 这 5 条都不是脱敏数据特有的，任何用友/金蝶多账簿导出都会有。已被代码防住，不依赖用户清洗做对。

### 10.4 映射陷阱（**对外测试要重点讲**）

科目余额表里：

- `期末余额(借)` = **原币**
- `期末本位币(借)` = **本币**

而平台标准字段里 `end_debit` 是**本币**、`end_debit_fx` 是**原币**（fx = 原币）。**这两个极易反着映射**，一反就把外币户的本币金额当原币、原币当本币，BKD 全表错。

自动映射目前会把 `期末余额(借)` 识别成 `end_debit`（错的），需要在字段映射页把：

```
end_debit    ← 期末本位币(借)      end_debit_fx    ← 期末余额(借)
open_debit   ← 期初本位币(借)      open_debit_fx   ← 期初余额(借)
cur_debit    ← 本期发生本位币(借)   cur_debit_fx    ← 本期发生(借)
ytd_debit    ← 本年累计本位币(借)   ytd_debit_fx    ← 本年累计(借)
```

**下一步应该把这条做成自动识别 + 映射页醒目标注**，否则每个客户都要手工纠一次。

## 11. 交给别人测试时的步骤

### 11.1 起服务

双击 `启动PTW平台.bat`（或 `程序/runtime/python/python.exe 程序/server.py`）。
左侧导航最后一个板块「三、底稿生成」。

### 11.2 先把数据灌进去（「一、导入与清洗」）

1. **科目余额表** → 导入 → 清洗（至少确认没有把外币行删掉）→ **字段映射务必核对 §10.4 那四条** →
   「一级科目」要能识别成 `库存现金/银行存款/其他货币资金` → 合并
2. **序时账** → 导入（多个文件就逐张导）→ 映射（`科目全名` → 科目名称、`借方/贷方金额` → 借/贷）→ 合并
3. 序时账如果是 **1,000,000 整行**，先怀疑导出被截断，报告里要写明

### 11.3 生成银行存款底稿（「三、底稿生成」→ 银行存款底稿页签）

1. 填资产负债表日（例如 `2026-06-30`）→ **预览**
2. 看到「将写入 N 个账户，其中 M 格需要人工补」→ **生成** → 下载
3. 打开 Excel 逐项核：

- [ ] `C.00 BKD` 明细行数 = 预览的 N；零余额账户没被删
- [ ] H 列合计 = 科目余额表里 1001+1002+1012 的期末本位币合计（**排除综合本位币行**）
- [ ] I（性质）和 J（是否函证）**整列是黄的**，且没有默认值
- [ ] 账号列左对齐、无科学计数、无丢前导零
- [ ] 合计行公式覆盖到最后一个数据行；勾稽行指向 `C.00 Lead`
- [ ] 「检查」表最后有「五、待确认清单」

### 11.4 生成费用底稿（费用底稿页签）

1. 先上传**账簿↔公司对照表**（两列：账簿名称 / 公司名称）——不上传的话 B 列会全黄
2. 填期间（默认 1–6）→ 预览 → 生成 → 下载
3. 核对：

- [ ] VC / VD 两张表各有数据，E 列合计与预览一致
- [ ] K 列（上期审定数）整列黄，L/M（变动额/变动率）**留空而不是等于本期金额**
- [ ] 插行后合计公式是 `SUM(E29:E末行)`，不是还停在 `E29:E33`
- [ ] 「费用检查」表里「账套映射」全部「精确」或「归一」，没有「未命中」

### 11.5 已知限制（不是 bug，别当 bug 报）

| 项 | 说明 |
|---|---|
| 「性质 / 是否函证」不填 | 属职业判断，工具只标黄。给了默认值反而危险 |
| 上期审定数不填 | 本次没有上年同期序时账，填 0 会让变动率全错 |
| 只做 BKD + Lead 公式 | OAR / TOD / G3 / C.01b / C.00b / C.02 未做（见 §5） |
| 脱敏账号是假号 | `010` 这类不能用于函证，只验证流程 |
| 不重算 Excel | 公式已写但没缓存值，用 Excel 打开会自动重算 |

### 11.6 出问题怎么报

把三样东西发回来：① 生成的两个 xlsx；② 「检查 / 费用检查」表整张；③ 预览页显示的账户数与标黄数。
有这三样，基本能定位是映射错了还是代码错了。

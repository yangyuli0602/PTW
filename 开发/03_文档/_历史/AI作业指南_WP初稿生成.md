# AI 作业指南 · WP 初稿生成（货币资金 / 销管费用）

> 读者：接手「WP 初稿生成」的 AI（或人）。本文只写**工具做不了、必须判断**的部分。
> 工具能做的（本年上数、TOD 抽样）在页面上点按钮就行，不要在本文里找。
> 依据：`03_文档/审计底稿上数逻辑说明_BKD_OAR_TOD.md` v2 第 10 章「自动化边界」。

---

## 0. 分工一句话

> **工具让数字对得上，AI 让判断站得住。**

| 级别 | 谁做 | 典型任务 |
|---|---|---|
| A 机械规则 | 工具，不打断 | 本年 BKD/Lead 上数、合计、勾稽、TOD 抽样、回归比对 |
| B 起草 + 确认 | 工具给建议值，人点确认 | 期末余额取数口径、TE/SAD、阈值、样本量 |
| **C 必须判断** | **AI 起草，人确认** | **上年数归集、OAR 变动原因、受限资金、分类结论** |
| D 禁止 | 谁都不做 | `+1`/`ROUND`/手填调平、自动下「无异常」结论 |

本文覆盖两个 C 级任务：**① 上年 WP → 上年数**、**② OAR 变动分析**。

## 任务一：上年 WP → 上年数

### 1.1 为什么要 AI 做

上年底稿是去年那套模板产出的，**每个客户 sheet 名、列位、表头行都不一样**。
工具里的正则识别能覆盖常见结构，但遇到改版就静默错位（比报错更危险）。
所以工具先把「这张表长什么样」摊开，由你判断。

### 1.2 输入

平台页面「WP初稿生成 → 货币资金 → 上年 WP → 导出结构探测包」，会给你一段 markdown，形如：

```
# 上年 WP 结构探测包
| # | 工作表 | 行数 | 列数 | 表头匹配分 | 推测表头行 |
| 1 | C.00 BKD | 142 | 15 | 19 | 9 |
| 2 | C.00 Lead | 74 | 18 | 6 | 36 |
...
## C.00 BKD（推测表头第 9 行，分 19）
r1  | cd8846d7-... | 标准工作底稿: C SWP 货币资金
r8  | TB | TB | TB | TB ...
r9  | 公司名称 | 科目名称 | 银行/存款机构名称 | 账号1 | 币种 | 期末账面金额（原币） | ...
r10 | 1A公司 | 库存现金 | 工商银行 | 6222... | 人民币 | 1234.56 | 1234.56 | ...
```

### 1.3 你要做什么

1. **挑出 BKD 明细表**：通常表名含 `BKD`，且首行有「公司名称 / 科目名称 / 银行 / 账号 / 期末金额」。
   匹配分 ≥16 基本就是它；但如果表名是 `明细`、`breakdown`、`附表1` 这种，按内容判断，别只看名字。
2. **定表头行**：**表头行 = 字段名那一行的行号**，不是第一行数据。
   注意有些模板的表头是两行（第 1 行分类、第 2 行借/贷），此时 `header_row` 取**第 1 行**，平台按两行合并识别。
3. **看数据区间**：从表头下一行开始，到最后一行明细为止；中间如果有「合计 / 小计 / 说明」行，不用特意排除，平台会按科目名过滤。
4. **回一份 JSON**：

```json
{
  "sheet": "C.00 BKD",
  "header_row": 9,
  "data_start": 10,
  "data_end": 135,
  "note": "第 9 行是字段名行，A 列编号/B 列公司/C 列科目，与 BKD 结构一致；第 137 行是合计，故数据止于 135"
}
```

### 1.4 判断依据（按这个顺序看）

| 顺序 | 看什么 | 说明 |
|---|---|---|
| 1 | 有「账号」或「银行/存款机构」列 | 货币资金 BKD 的标志，普通明细表没有 |
| 2 | 有「期末账面金额」并分原币 / 本币两列 | 有外币主体时一定是两列 |
| 3 | A 列是编号、B 列是公司名 | 标准 Skywind 底稿的组织方式 |
| 4 | 数据行数 ≈ 账户数（几十到几百） | 上千行大概率是序时账，不是 BKD |
| 5 | 末尾有 `SUM(...)` 合计、下一行有 `RX`、再下一行有 `- Lead` 勾稽 | 这是底稿的典型尾部 |

### 1.5 硬约束（违反就是错）

- **不许猜列**：看不清就回 `{"error": "第 3 张表列头被合并单元格遮挡，请人工确认"}`，不要编一个 header_row。
- **不许改数**：你只负责"这是哪张表、表头在第几行"，不要动金额、不要补缺失行。
- **必须给 note**：一句话说明判断依据，人要能复核。
- **对不上要报**：解析后平台会显示「解析出 N 个账户、合计 X」，如果与上年 Lead 的期末审定数差得离谱，
  说明表头行选错了，回去重看，别硬交。

### 1.6 平台怎么用你的结果

```
POST /api/build/prior/apply
{"fid": "<上传后的文件id>", "spec": {"sheet": "...", "header_row": 9}}
→ {"rows": 126, "sum": 100067778.85, "sample": [...]}
```

返回的 `sum` 要和上年 Lead 的「期末审定数合计」对得上（差异 < 0.01）。
对不上就说明 header_row 或 sheet 选错了。

## 任务二：OAR 变动分析（带链接的千元口径表）

### 2.1 OAR 是什么

OAR = 报表口径分析表，**千元为单位**，由 Lead 汇总公式链接而来，不是手填。
每一行是一个科目/项目，列通常是：本期审定数、上期审定数、变动额、变动率、是否需进一步调查、说明。

**要你做的只有一件事**：对「变动绝对值 ≥ TE」的项目，读序时账，说清楚
**是哪家公司、什么性质的事项**造成的。

### 2.2 计算口径（工具算，你复核）

```
变动额 = 本期审定数 − 上期审定数
变动率 = 变动额 ÷ |上期审定数|        （上期为 0 时留空，不要写 100%）
超阈值 = |变动额| ≥ TE                （TE 从 Lead 的 C4 读，不要自己假定）
```

货币资金常见的"正常变动"（**不要花力气解释**）：

- 定期存款到期/新购：在「银行存款」与「其他货币资金/定期存款」之间搬家，总额不变
- 外币折算差：汇率变动导致的差额，说明汇率与折算方法即可
- 受限资金重分类：BKD P 列 → Lead I 列，总额不变、列示变

### 2.3 分析步骤

1. **定位差额**：拿到某科目本期与上期审定数，算出变动额。
2. **在序时账里找承接它的凭证**：按 科目 + 期间 过滤，按金额降序，看前 20 笔。
   优先找「单笔金额接近变动额」或「几笔加起来等于变动额」的凭证。
3. **读摘要，判断性质**：摘要里通常有公司简称、业务类型（收付款、划转、到期、结汇）。
   把摘要原文贴上，不要改写。
4. **归因到一个具体主体/事项**，写成一句话：
   > 「9H 公司美元户本期新增欧元定期存款 1.17 亿（折算 9,081 万人民币），
   > 凭证 记-2026-03-0012，摘要"欧元定期存款存入"」
5. **配不上就明说**：「变动 2,300 万，序时账未见对应单笔或组合凭证，可能为期初余额调整，
   需向客户询问」——**这比编一个原因好一百倍**。

### 2.4 输出格式

```json
[
  {
    "account": "银行存款",
    "period": "2026-09",
    "cur": 1422875244.88,
    "prior": 1200000000.00,
    "delta": 222875244.88,
    "company": "9H公司",
    "nature": "新增欧元定期存款",
    "evidence": ["记-2026-03-0012 摘要：欧元定期存款存入 11,691,344.42 EUR"],
    "confidence": "高",
    "needs_client": false
  }
]
```

`confidence` 只能填 高 / 中 / 低；`needs_client=true` 表示要问客户，不要为了好看把它填成 false。

### 2.5 硬约束

- **不许抹平**：差额就是差额，不许用「其他」「零星」把余额凑上。
- **不许编摘要**：`evidence` 必须是序时账里真实存在的摘要原文或凭证号，编一个就全废。
- **不许下结论**：「未发现异常」「无需进一步程序」这类结论**只能人写**，你最多写「已核对，未见对应凭证」。
- **不确定性要标出来**：配不上、只能部分解释、摘要看不懂，都要在 `note` 里写清楚。

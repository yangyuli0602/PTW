> 回应：飞书《清洗验收结论_2026-09-30.xlsx》「工具能力试跑」+《生成一级科目_核算维度明细优先_实现说明.md》

## 1. 结论：报告里说的三条都成立

先说清楚哪些是真 bug、哪些不是，避免各改各的。

| 报告里的现象 | 是否成立 | 定性 |
|---|---|---|
| 先删「所有账簿」再填充 → 0 行 | **成立** | 操作顺序问题，但工具没拦住，也没提示 |
| 全局填充 → 删「所有账簿」→ 只留维度明细：丢 295 个无明细科目、差 +9.5 亿 | **成立** | 前置步骤删掉的，`add_acct_path` 救不回来 |
| 全局填充 → 删「所有账簿」→ 生成一级科目：行数/辅助/金额都不对、差 −21.4 亿 | **成立** | **动作本身的 bug**：同码多行按「金额最大」只留 1 行，把维度明细删了 |
| 科目全称重复父名（`银行存款_银行存款_…`） | **成立** | 编码 `1002_1002` 分两级都指向同一科目名，拼接时重复 |
| 科目编码保留维度后缀（`1002_1002`） | 成立，但**未改动** | 属于「编码规范化」，会改变映射后 acct_code 的语义，需单独确认（见 §5） |

用最小样例复现（`tmp/repro_l1.py`），老配方的结果：

```
输入 9 行（含 1002 两个维度明细、1122 一个客商明细、6602 无明细、跨币别）
老配方 → 5 行，全部是「核算维度为空」的汇总行
         中国银行 600 / 招商银行 400 / 客户甲 500 / 花旗 700 全部被删
         金额合计 2700 —— 恰好对，所以从金额上看不出错
```

金额对、行数错，这是最危险的一种：后面四项检查照样能过（因为汇总行金额就是明细合计），
但底稿里已经没有账户级明细，函证、对账单、截止性测试全部做不了。

## 2. 改了什么

### 2.1 三个新参数（全可选，不传 = 行为与 V1.2.01 完全一致）

| 参数 | 类型 | 默认 | 作用 |
|---|---|---|---|
| `aux` 核算维度列 | 多列 | 空 | 判断「这个科目有没有明细」。任一列非空即视为明细行 |
| `detail_first` 有明细时只保留明细行 | 关/开 | 关 | 分组内：有明细只留明细、删汇总行；无明细留 1 行科目行 |
| `group_cols` 分组列 | 多列 | 空 | 留空自动带币别列。多币种必须按币别分组，否则 USD 的明细会把 EUR 的汇总行带走 |

分组维度 = `主体 + 科目编码 + 分组列`，逐组独立判断。

### 2.2 判断规则

```
for each (主体, 编码, 分组列):
    if 同主体内存在更长编码以本编码为前缀:   # 非末级
        整组删除
    elif 组内存在 aux 非空的行:              # 有明细
        只留 aux 非空的行，删掉汇总行
        不按同码去重（多条维度明细共用同一编码很正常）
    else:                                     # 无明细
        留 1 行（同码多行按金额绝对值最大保留）
```

### 2.3 剔除留痕分三类

以前所有被删的行都记成「非末级科目行或同码重复行」，看不出删的是汇总行还是真实明细。
现在分开记：

- `非末级科目行`
- `有明细的汇总行`
- `无明细科目的同码重复行`

哪一类数量明显不对，一眼能看出来。

### 2.4 顺序错了会拦一下

任何一步把整表从 N 行变成 0 行，该步的说明会变成：

> ⚠ 本步把 7416 行清成了 0 行。通常是参数或前置步骤顺序不对
> （例如先删了「所有账簿」汇总层，导致科目编码全空、无值可填）

以前这种结果看起来就像「数据是空的」，很容易被当成原始数据问题放过。

### 2.5 科目全称去掉相邻重复段

`1002_1002` 用 `_` 拆成两段、都指向同一科目名，以前拼成 `银行存款_银行存款`。现在相邻重复段跳过，得到 `银行存款`。

## 4. 用之前要按这个顺序

```
文本归一
  → 全局向下填充（科目编码、科目名称，不要按账簿分区）
  → 按关键词删「所有账簿」层
  → 生成一级科目（核算维度列=核算维度名称，明细优先=开，分组列=主体+币别）
```

「所有账簿」层必须删（否则和账簿明细重复计），但**必须在填充之后删**。

## 5. 没做的两件事

**① 真实文件的 5,813 / 495 两个数字没验。** 那两个多账簿源文件（7,416 行 / 640 行）我手上没有，
只用同构的最小样例验证了逻辑。要按报告 §5 的基线回归，需要把这两个文件给我。

**② 科目编码规范化（`1002_1002` → `1002`）没做。** 原因是它会改变映射后 `acct_code` 的值，
进而影响第三、四组检查的分组口径，属于「改语义」而不是「修 bug」。
如果确实需要，建议加一个默认关闭的开关「规范化科目编码」，开启后另存原编码到「原科目编码」列。
这一条要不要做、默认开还是关，需要你定。

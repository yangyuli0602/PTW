## 0. 一句话

底稿不是"填数字"，是四层（v2 在 OAR 旁边并列了 SRM 波动分析，并新增 G3 预付/待摊一条独立链）：

```
TB / 序时账 / 明细账
  └─ BKD   明细底稿（逐账户 / 逐科目 / 逐供应商）—— 原始录入点
       └─ Lead   科目汇总 + 审计调整 + 与 TB 勾稽
            └─ OAR / SRM   千元报表口径 + 管理层波动分析
  └─ TOD   费用抽样总体（池 → 剔除 → 关键项 → 抽样 → 测试表）
  └─ G3    明细账BKD（供应商级+账龄）→ G.00 Lead → G.01 核对 → G.02.2 详细测试
```

**只把最底层明细（TB 明细、序时账、明细账）写进 BKD / 样本池，往上全部用公式引用。** 把汇总数直接贴进 OAR = 下期失去可追溯性。

**四个原始录入点（v2 新增第 4 个，写代码时按这个卡片对）**：

| # | 位置 | 粒度 | 谁写 |
|---|---|---|---|
| 1 | `C.00 BKD` **I 列**（本币-人民币） | 主体 × 银行 × 账号 × 币种 | 工具从 TB 写，A/E/J/L 是公式回捞 |
| 2 | `VC/VD BKD` **E 列**（本期账面数） | 账簿 × 科目编码 | 工具从序时账/TB 写 |
| 3 | `样本池-TOD` **K 列** | 序时账逐笔 | 工具从序时账派生 |
| 4 | `G3 明细账BKD` **O 列**（期末本位币） | 主体 × **供应商** | 工具从明细账写，Q/R–Y 全公式 |

> 除这四列（及其配套的 B/C/D/F/G/H、备注列、人工判断列 P）之外，**任何格子都不该由工具"贴数"**。

## 1. 铁律（改代码前先背下来）

| # | 规则 | 反面做法 |
|---|---|---|
| 1 | 单一数据源：一个数字只有一个录入点 | Lead/OAR/C.01b 手填 |
| 2 | 写公式时**同时写 `<v>` 缓存值** | 只写公式，阅读器显示空白 |
| 3 | 口径表驱动，公式里不硬编码中文科目名 | `SUMIFS(...,"银行存款")` 写死 |
| 4 | **完整性优先**：0 余额、已销户账户必须保留（本期 126 户里 55 户为 0） | 按非零过滤后上数 |
| 5 | **差额必须解释**，禁用 `ROUND` / `+1` / 手填调平 | `OAR 26630` 的 `+1` 就是历史反例 |
| 6 | 未取得的数据**留空 + 标黄 FFFF00** | 填 0 或"待定" |
| 7 | 每张表至少一个「合计—明细」或「本表—TB」勾稽格，结果须为 0 | 全靠肉眼 |
| 8 | 重跑幂等：先清空目标区再写；人工覆盖放独立列/sheet | 重跑残留上次数据 |
| 9 | **关键参数只引用不硬编码**：TE 从 `PMTE!$B$5` 读（本期 **779,338.37**），汇率/阈值同理 | 把 785,860.20 或 779,338.37 写死在代码里 |
| 10 | **人工判断必须留痕**：凡 B/C 级判断（见 §7.5），写清"谁、依据什么、结论" | 工具静默替人下"无受限/无调节项" |

> 第 9 条有实际后果：TE 变动会带动 C.00 Lead `D14:D18`、`E14`、C.02 `B8`、
> Uexp 的 `D8:D11`、TOD 关键项阈值、G.00 `AB` 列的异常判定，**一处硬编码全链条错**。

## 2. ⚠️ 最关键差异：本地模板 ≠ 实际底稿

本地 `data/bkd_tpl/C SWP 货币资金 模板 V7.xlsx`（15 个 sheet，干净模板）与文档描述的

|---|---|---|
| A | — | **编号**（`=XLOOKUP(B10,口径mapping表!C:C,口径mapping表!A:A)`） |
| B | 公司名称 | 公司名称 |
| C | 科目名称 | 科目名称（只允许 `银行存款` / `其他货币资金`） |

**结论：930 版比本地模板多 A、I（以及 v2 新增的 P）三列，J 之后整体右移一格。** 现有代码：
- 只有一个本币金额（写 H），**缺 I 的「人民币」金额** → 港、新主体会错
- 性质写在 I（930 版应在 J）
- 合计用 `SUM(H…)`，最终版是 **`I137 = SUM(I10:I135)`**
- 勾稽写 `=H…-'C.00 Lead'!F41`，最终版是 **`I139 = I137-'C.00 Lead'!F46`**

> 所以：**动手第一步必须是拿到 930 那份真实底稿**，不能再照空白模板猜列位。

## 4. 上数契约（写代码时照这个接口）

| 输入 | 货币资金 `C.00 BKD` | 费用 `VC/VD BKD` | G3 `明细账BKD`（v2 新增） |
|---|---|---|---|
| 来源 | TB（按账户） | 序时账 / TB（按科目） | **明细账 SL（按供应商）** |

| 必填（工具写） | B/C/D/F/G/H/I/K | B/C/D/E | A/B/D/E/G/N/O |
| 人工判断列 | J（性质回捞）、P（受限资金） | — | **C（关联方）、F（款项性质）、P（审计调整）** |

**货币资金账户主键 = `科目名称 + 银行名称`（C&D），不是账号。** 账号会因为升级/变更而变，
模板正是靠 C&D 去上期表把账号和性质捞回来。**上期表缺失时留空 + 提示人工补，不要自动编号。**

**G3 主键 = `公司名称 + 供应商 + 款项性质`（A+B+F）。** 同一供应商可能同时有预付产能款和待摊费用，
只按供应商去重会把两笔并成一笔、账龄桶也会错。

## 5. TOD 的两个算法要点（最容易写错）

### 5.1 剔除标签判定顺序（顺序错了会互相吞）

```
① 性质类（直接归类）：职工薪酬 / 股份支付 / 使用权资产折旧 / 固定资产折旧 /
   无形资产摊销 / 长期待摊费用摊销
   ⚠ 必须先判「使用权资产折旧」，再判「折旧费」——否则前者被后者吞掉
② 预提冲销（成对识别）
③ 负值（其余红字）
④ 零发生额（金额=0 直接不进池，不占标签）
⑤ 未命中 → 「否」，进入抽样总体
```

### 5.2 预提冲销配对（净额必须为 0）

```text
分组键 key = half(month) + "|" + code3 + "|" + abs(amount).toFixed(2)
             half = month <= 6 ? 1 : 2      // 预审段 / 剩余段各自独立配对
组内：pos 按金额降序、neg 按金额升序，1:1 配对，双方都打「预提冲销」
```

- **必须按 half 分组**：跨期配对会把 1-6 月净额挪到 7-9 月，两段都不为 0
- 验收：`SUMIFS(K, M, "预提冲销") = 0`（浮点误差 < 1e-6），本期 538 行净额 0.00
- 配不上的行不强配，留作「否」或「负值」

## 7.5 自动化边界（v2 第 10 章 → 落到 PTW 该不该做这个按钮）

**这是 v2 最该先读的一节**：作者把 30 个环节逐个标了 A/B/C/D，等于替我们划好了功能边界。

| 级别 | 底稿含义 | PTW 里应该做成 |
|---|---|---|
| **A 全自动** | 输入确定、规则唯一、结果可机器校验 | 默认执行，只附校验结果，不打断用户 |
| **B 起草 + 确认** | 规则可算，但参数/口径要人定 | 预填建议值 + 依据，用户点确认才写入 |
| **C 必须人工** | 职业判断 / 外部证据 / 管理层沟通 | 只生成"待填清单 + 该填哪个格"，**不给默认值** |
| **D 禁止** | 会破坏可审计性或误导使用者 | **代码里不实现**，连入口都不留 |

**A（直接做）**：映射解析、上期回捞、BKD 去重与保留 0 余额、币种折算、所有合计/结构比/变动率、
Lead SUMIFS 与 Diff、样本池过滤归一化、性质标签与预提冲销配对、G3 账龄分桶、Check 与回归比对。

**B（给建议值）**：期末余额取数口径（ytd/cur/end）、TE/SAD 取值、波动调查"是/否"、
关键项阈值与样本量、C.02a 汇率与差异容忍、程序索引。

**C（只准备不落笔）**：账户性质与是否函证、**受限资金识别与金额**、受限重分类、C.01b 范围、
C.00b 分类结论、C.02 调节项结论、审计调整分录、抽样执行与例外评价、G3 款项性质/关联方、
所有叙述性结论（NB / 异常说明）。

**D（不实现）**：`+1`/`ROUND`/手填调平 Check、自动填对账单金额、自动下"无调节项/无受限/无减值"结论、
修改非目标 sheet。

**工具必须产出 5 个交接物**（少一个，人就得回头翻底稿）：

1. **待确认清单**：新增账户、无上期账号/性质的账户、P 列为空但 J 列显示"保证金/受限"的账户
2. **差异清单**：所有非 0 的 Check（科目 / 主体 / 金额 / 可能原因）
3. **黄标清单**：所有留空并标黄的单元格及原因
4. **未匹配清单**：TOD 配对失败的正/负金额、G3 无账龄的供应商
5. **回归报告**：与 §8 基准逐项比对

> **AI 负责"让数字对得上"，人工负责"让判断站得住"。**
>
> 直接后果：PTW 的 BKD 板块能做到 A 级（填明细、算合计、出 Diff、出待确认清单），
> 但**不能替用户判定受限资金、不能替用户下"无调节项"结论**。这不是能力不够，是审计上不允许。

| 写 C.00 BKD 明细、超 6 行自动插行 + 平移合并单元格 | `_fill_bkd()`（**列位需按 §2.1 改**） |
| 写 C.00 Lead 打链接 | `_fill_lead()`（**勾稽引用需按 §2.1 改，现为 F41，应为 F46**） |
| C.03 Cutoff 抓序时账银行间转账 | `find_transfers()` + `_fill_cutoff()` |
| 生成检查表 | `_build_check_sheet()` |
| zip 级 XML 改写（不丢模板部件） | `build_book_xlsx()` 里的写法可直接复用 |

明确缺口（V1.2 要补）：

1. **列位对齐最终版**：加 A 编号、加 I（本币-RMB）、性质移到 J、函证 K、理由 L、Notes M、**P 受限资金**
2. **H 与 I 两个本币金额**：港、新主体 H=美元、I=人民币，普通主体两者相等
3. **合计/勾稽列改 I**，`I137` / `I139` 位置按实际底稿动态定位（不要写死行号）
4. **口径mapping 表驱动**：A 列编号、费用 V 列类别，都要 XLOOKUP，不许硬编码
5. **OAR 层完全没有**：千元公式、`/1000` 不舍入、OAR-管理/销售
6. **TOD 完全没有**：样本池、标签算法、预提冲销配对、总体/剔除/关键项/抽样；
   且标准做法是**独立工作簿**（§2.4.2），不是塞在 U_exp 里
7. **派生表没有**：C.01b / C.00b / C.02 / C.02a
8. **未取得资料标黄机制**：需要一套"留空 + FFFF00 + Notes 说明"的统一写入函数
9. **calcChain 处理**：写公式后删 `xl/calcChain.xml` + 设 `fullCalcOnLoad`
10. **费用侧整块是空的**：现有 `modules/bkd/` 只做货币资金，`VC/VD BKD`、`Uexp.00 Lead`、
    `01.3 法律费用`、`01.4 截止性测试` 一行代码都没有
11. **列定位要改成按表头文字匹配**：模板会因项目增列（§2.4.1），不能按列字母硬编码。
    复用已有的 `BKD_SPEC` + `map_columns()` 正则匹配即可
12. **Lead 参数缺失要报错**：`Uexp.00 Lead` 的 C4/C7 空时不能默认 0，要提示"请先填重要性/货币单位"
13. **G3 整块是空的（v2 新增）**：明细账 BKD（供应商级 + 账龄桶 R–W）、G.00 Lead、G.01 核对、
    G.02.2 详细测试，一行代码都没有；且账龄要"按受益期终点落桶"，不能按供应商汇总后拆
14. **受限资金 P 列没有**：写/读 P 列、`SUM(P)=Lead!I44` 对账、"只在 P 列记一次"的口径都没有
15. **待确认/差异/黄标/未匹配/回归 五个清单没有**（§7.5）——这是 A 级功能里最容易被漏掉、
    但对用户价值最高的一块：工具不产出清单，人就只能自己对着底稿翻

> 第 13 项的工作量约等于整个货币资金 BKD（97 行 + 6 个账龄桶 + 3 张汇总表），
> 不要低估；但它**逻辑更简单**：没有多币种、没有上期回捞账号、没有 P 列判断，
> 只有"按供应商汇总 + 按受益期分桶 + 三段勾稽"。

### 10.1 费用侧开工建议（新板块 or 子页）

按项目约定「新增独立功能优先隔离实现」，两个选项：

- **A（推荐）**：在 `modules/bkd/` 里加子页签「费用 BKD」，共用 `core.py` 的模板读写工具
  （zip 改写、插行、写公式+缓存值），但费用逻辑独立成 `expense.py`，互不污染
- **B**：新建 `modules/expense/` 板块，manifest 独立

爬坡顺序建议（v2 调整）：

```
G3 明细账BKD  →  VC/VD BKD（E 列）→ Lead 汇总 → 截止性测试
   → TOD 样本池 → TOD 汇总 → OAR  →  最后回到货币资金 C.00 全套
```

- **拿 G3 试手，不要拿 C.00 试手**。G3 没有多币种、没有上期账号回捞、P 列是人工的，

## 11. 和已完成功能的关系（别搞混）

| | 「银行存款账面信息表」（V1.1.03/1.1.04 已做） | C.00 BKD（V1.2 待做） |
|---|---|---|
| 用途 | 上传给**函证系统**的账面信息 | **底稿明细**，向下勾稽 Lead/OAR |
| 模板 | `1.银行存款-账面模板.xlsx`（B~K 十列） | `C SWP 货币资金`（A~M 十三列） |
| 粒度 | 主体 × 科目 × 币别（**按账号分组**） | 主体 × 银行 × 账号 × 币种（**主键是 科目+银行名**） |
| J/K 列 | 一律「是」/ 留空 | 是/否要判断，理由否必填 |
| 金额 | 原币 + 本币两列 | 原币 + 本币 + 人民币三列 |

两者**取数逻辑可共用**（都从 tb 拿），但输出结构、主键、必填字段都不同，不要合并成一个函数。

**第三个东西：费用 BKD（VC.00 / VD.00）** —— 与上面两个都不同：

| | 账面信息表 | C.00 BKD（货币资金） | VC/VD BKD（费用） |
|---|---|---|---|
| 数据源 | tb（余额表） | tb（余额表，按账户） | **序时账 / tb（按科目）** |
| 粒度 | 主体 × 科目 × 币别 | 主体 × 银行 × 账号 × 币种 | **账簿 × 科目编码** |
| 录入点 | 全部列 | I 列（本币RMB） | **E 列（本期账面数）** |
| 上期依赖 | 无 | 上期 BKD 回捞账号/性质 | 上期 BKD 回捞 K 列上期数 |

三者的共用部分只有「**zip 级改写 + 插行 + 写公式和缓存值**」这套写文件的工具函数；
业务口径、主键、勾稽目标各不相同，**不要试图写一个万能上数函数**。

**第四个东西：G3 明细账 BKD（v2 新增）** —— 供应商粒度，和上面三个都不一样：

| | 账面信息表 | C.00 BKD | VC/VD BKD | **G3 明细账BKD** |
|---|---|---|---|---|
| 数据源 | tb 按科目 | TB 按账户 | 序时账按科目 | **明细账 SL 按供应商** |
| 粒度 | 主体×科目×币别 | 主体×银行×账号×币种 | 账簿×科目编码 | **主体×供应商×款项** |
| 录入点 | 全部列 | I 列 | E 列 | **O 列** |
| 特色 | J/K 一律是 | 三列金额 + P 受限 | 变动阈值 + 调查判断 | **账龄 6 桶 + 审计调整 P** |
| 上期依赖 | 无 | 回捞账号/性质 | 回捞上期数 | 年初 H/I 结转 |

> G3 是**唯一带账龄的 BKD**。账龄（R–W）必须"按单笔预付款的受益期终点落桶"，
> 这套逻辑不能套到货币资金或费用上；反过来 C.00 的多币种三列金额也不能套到 G3。

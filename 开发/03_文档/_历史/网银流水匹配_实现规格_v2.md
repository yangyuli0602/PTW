# 网银流水 × 账面账户清单 — 匹配实现规格 v2

> 这份文档是给**实现方**的任务书，不是复盘说明。读完应能独立实现，且产出的结果**可复现、可复核、可反查**。
> v1（`网银流水mapping_生成逻辑说明.md`）是一次性脚本的复盘，其中的若干启发式规则在 v2 中被明令禁止，原因逐条写在 §3。

---

## 0. 一句话说清任务

把一堆**格式各异的原始网银流水文件**，逐个判定"它属于账面清单里的哪一个银行账户"，并**在输出的每一行里写清楚判定的证据在哪**（文件名第几段 / 哪个 sheet 的第几行第几列 / 哪个表头字段 / 抽到了什么值）。

**不做的事**：不核金额、不做截止测试、不判断期间完整性。这些是二期。

---

## 1. 关于要不要用大模型

**结论：不要用。**

理由（按重要性排序）：

1. **账号是精确字符串**。归一化后（去非数字）是 `1 == 1` 的判定，规则可以 100% 确定。让模型读是"用不精确的工具做精确的活"。
2. **不可复现**。审计底稿要求"同一批输入，任何时候重跑，结果逐字节一致"。模型输出不满足这一点。
3. **幻觉在账号场景是灾难**。`755932641710201` 被改写一位，表面上仍是合理账号，但指向了另一个（或不存在的）账户，且**没有任何自动检查能发现**。
4. **成本与依赖**。207 份文件、几百个 sheet，规则跑一次几秒；走模型要几分钟、要额度、要联网/内网模型可用性保障。
5. **证据链要求反过来否定模型**。本任务要求写出"证据在 C5 单元格"，这恰好是确定性程序天然能做的事，模型反而做不到（它只能说"我看到账号是……"）。

**允许使用大模型的唯一场景**（可选，且必须人工确认，不得直接写结论）：

- 遇到**从未见过的表头措辞**，让模型生成一个适配器草案（"这个表哪个列是本方账号"），人工确认后固化成规则再入库；
- **扫描件 PDF** 的版面理解（本项目 v1 中的 `historydetail455.pdf`）。

即使在这两个场景，模型的输出也只能是"候选 + 待确认"，**不得直接进入"已匹配"**。

## 2. 输入

| 输入 | 形态 | 说明 |
|---|---|---|
| 原始网银流水 | 一个文件夹（可含子目录） | 后缀混杂：`.xlsx` / `.xls` / `.pdf`；同一目录下可能有 `.files` 辅助目录 |
| 账面账户清单 | 一份 excel | 每行一个账户，至少含：账户名称（公司）、账号、开户银行；建议含币种、期末余额、账户状态 |

**账户清单的读取要求**：

- 不写死 sheet 名和起始行，用表头锚点定位（见 §7.1）。列顺序可变，靠表头文字映射。
- 账号列**必须按文本读**，防止 `755932641710201` 被读成 `7.55933E+14`。
- 如果清单里同一账号出现多行（不同币种），**账号+币种**才是账户主键，不可按账号去重。
- 必须区分"零余额/已销户"与"非零余额"，后者才是"可能漏取流水"的嫌疑对象。

## 3. 明令禁止的 5 种做法（v1 里的坑）

违反任何一条，结果即视为不合格，**即使最终数字看起来对**。

### 3.1 禁止"取文件中最早出现的账号作为本方账号"

v1 §3.2-③ 与 §3.3 用"最早出现"当本方账号。这是错的，因为：

- 银行导出的版式里，**表头（含本方账号）通常在前**，但**交易明细的对方账号也可能出现在正文更早的位置**（如先有"账户信息"区块列对方户名，后有明细）；
- 更致命的是：当**本方账号不在清单里**时（如交行保证金账户 `443899999703000099720`），"最早出现的清单账号"必然是**对方账号**，于是文件被记成"已匹配"，把本该暴露的"流水有账无"变成了假成功。

**改法**：拿不到"本方账号"字段就进 `待确认-无本方字段`，只列候选，不定案。

### 3.2 禁止把"出现次数最多的值"当本方账号

v1 §3.2-③ 对 `historydetail795.xlsx` 用"该列众数"。问题是：**一个文件含多个账户时，众数必然选错，且掩盖了"应拆多行"这一事实**。

**改法**：该列取值**不唯一**即判定为多账户文件，按 §7.4 拆行。

### 3.3 禁止用"文件名去非数字后子串包含"匹配

v1 §3.1：`bkd.digits in only_digits(filename)`。两个问题：

- **方向不对称**：文件里是短号（`03006017389`）、清单里是长号（`0039294103006017389`）时能过；反过来（文件里带分行号 `011672789001`、清单里是 `672789001`）就漏；
- **假阳性**：连续数字拼接后，日期段+流水号段可能恰好包含某个 8 位以上的账号片段；且允许一次命中多个账号，一份文件被挂到两个账户上。

**改法**：见 §6，token 化 + 双向后缀 + 唯一性裁决。

### 3.4 禁止对 `.xls` 做字节流扫描

v1 §3.3：读前 8MB，用 latin-1 / utf-16le 解码，去非数字后找账号。失效场景：

- 账号若以**数字型单元格**存储（BIFF `NUMBER` 记录），文件里根本没有那几个字符，扫描必漏；
- 原始字节流跨记录边界拼接，会造出**并不存在的伪账号**；
- 无法给出"证据位置"，直接违背本任务的核心要求。

**改法**：见 §7.3，用 OLE2 + BIFF8 结构化解析。

### 3.5 禁止用 MD5 作为唯一去重手段

MD5 只能抓"字节完全相同"。抓不到最常见的重复形态：**同一账户、不同导出区间、期间重叠**（`0101-0331` 与 `0101-0630`）。

**改法**：MD5/sha1 只用于"完全重复"标注；业务去重另用交易指纹（§9.2）。

## 5. 总流程

```
A 枚举 + 指纹分流
      ↓
B 账户清单载入（表头锚点）
      ↓
C 文件名取证（每个文件都做）
      ↓
D 内容取证（仅当 C 无结果，或需要交叉校验时）
      ↓
E 裁决（唯一性 + 冲突检测）
      ↓
F 双向差异（有账无流水 / 有流水无账）
      ↓
G 产出（xlsx + jsonl）
```

与 v1 最大的结构差异：v1 是**阶梯短路**（文件名命中就 `continue`，内容不再看），v2 是**并行取证 + 统一裁决**。差别在于：文件名判定错了，v1 没有任何机会纠正；v2 会拿内容去校验它并报"冲突"。

## 6. 文件名取证（严格版）

### 6.1 取 token

从文件名（**只要文件名，不含目录**）中按非数字切分，取所有**连续数字长度 ≥ 8** 的片段，保留其在文件名中的位置：

```python
tokens = [(m.group(), m.start()) for m in re.finditer(r"\d{8,}", name)]
```

同时保留"文件名里的银行名/公司名"作为辅助信号（用于 §6.3 的消歧）。

### 6.2 与账户比对

```python
def relate(token, acct_digits):
    t, a = token, acct_digits
    if t == a:
        return "equal"                  # 完全相同
    if len(t) >= 8 and a.endswith(t):
        return "acct_ends_with_token"   # 文件里是短号（丢了前缀/分行号）
    if len(a) >= 8 and t.endswith(a):
        return "token_ends_with_acct"   # 文件里带分行号/多余前缀
    return None
```

长度差约束（`diff = abs(len(a) - len(t))`）：

| diff | 处理 |
|---|---|
| 0 | 置信度 **高** |
| 1–3 | 置信度 **中** |
| 4–10 | 置信度 **低**，且**必须**通过 §7 内容校验才能定案 |
| > 10 | 不算命中 |

> 参考：真实案例 `03006017389`(11 位) ↔ `0039294103006017389`(19 位)，diff = 8，属于 4–10 档；`112059423` ↔ `0112059423`，diff = 1。

### 6.3 多候选裁决

一个文件的所有 token、所有账户，构成命中集合：

1. **恰好 1 个账户命中** → 取之，置信度按 §6.2。
2. **同一 token 命中多个账户**（互为后缀关系必然发生）→ 取 **digits 最长**者（更具体），其余写入备注"另有 N 个账户符合后缀关系，已按最长优先"。若最长者不唯一 → 转 `待确认-文件名多候选`。
3. **多个不同 token 分别命中不同账户** → 一律 `待确认-文件名多候选`，列出全部候选。**不得**默认取第一个/最长/最先出现的。
4. **0 个命中** → 进入 §7 内容取证。

### 6.4 为什么文件名也可能错

文件名里的账号可能是**对方账号**（如"XX公司_付款_对账单"）。所以：

- 仅凭文件名定案的，置信度最高只能是 **中**，状态记 `已匹配-文件名`；
- 若该文件的内容能抽出本方账号，**必须**做一致性校验：
  - 一致 → 升级为 `已匹配-文件名+内容一致`，置信度 高；
  - 不一致 → **降级为 `待确认-证据冲突`**，两个值都列出来。这一条是 v2 相对 v1 最关键的行为变化。

## 7. 内容取证

### 7.1 表头锚点定位（不要写死行列号）

用"标签文字 + 值在标签的相对位置"定位，而不是记录"C5"：

```python
ACCOUNT_LABELS = [
    r"本方账号", r"本方帐号", r"本方账户", r"选择账号", r"交易账号",
    r"查询账号", r"账户号码", r"账号", r"帐号", r"卡号", r"Account\s*(No|Number)",
]
```

定位优先级：

1. **标签右侧第一个非空单元格**（最常见：`本方账号 | 755932641710201`）；
2. **标签下方第一个非空单元格**（纵向表头）；
3. **标签所在列的整列取值**（明细表里每行都重复本方账号）。

同一 sheet 内命中多个标签时，按 `ACCOUNT_LABELS` 顺序优先（"本方账号" > "账号"）。

### 7.2 必须记录的证据

无论走哪条路，**必须**产出：

```
location = f"Sheet「{sheet}」!{cell_coord}"     # 例如 Sheet「账户明细」!C5
label    = 命中的表头原文                        # 例如 "本方账号"
value_raw = 单元格原值转字符串                   # 不做任何清洗
```

做不到这三项的内容匹配，**视为无效**，降级为 `待确认`。

### 7.3 分格式处理

**(a) `.xlsx`**

- 用 `openpyxl`。若 sheet 声明的 dimension 明显小于实际（如 `max_row=1` 但有数据），用 `read_only=True` + `ws.reset_dimensions()` 重读；**注意** `reset_dimensions()` 只存在于只读模式，普通模式下调用会 `AttributeError`。
- 扫描范围：前 **80 行 × 40 列**（不是 40×30，v1 的截断会漏掉表头在合并单元格或页脚的文件）。若前 80 行无命中，回退整表扫描（单文件成本可接受）。
- 若一个 sheet 无命中，换下一个 sheet，最多 5 个。

**(b) `.xls`（BIFF8）**

- 先看**文件头**，不要信扩展名：
  - `D0 CF 11 E0 A1 B1 1A E1` → OLE2 复合文档，走 BIFF8；
  - `PK` → 其实是 zip，按 `.xlsx` 处理；
  - `3C 68 74 6D 6C` / 含 `<table` → **HTML 伪装成 .xls**，走 (c)；
- BIFF8 解析用纯标准库实现（OLE2 扇区 + `SST` 共享字符串 + `LABELSST`/`NUMBER`/`RK`/`MULRK` + `CONTINUE` 拼接），产出 `[[cell, ...], ...]`，**保留类型**（str / float / datetime / None）。平台项目 `core/xlsread.py` 已有可用实现（约 470 行，零依赖），可直接移植。
- 数字型单元格里的账号（`7.55932641710201e14`）按 `int()` 还原为字符串，**不要**用浮点格式化（会引入 `.0` 或精度损失）。
- 加密文件（OLE 内 `EncryptedPackage` 流 / BIFF `FILEPASS` 记录）→ `待确认-加密`，不要尝试破解。

**(c) HTML 伪装表**

用标准库 `html.parser` 解析 `<table>`，按行列还原二维表，之后同 (a) 的锚点逻辑。注意这类文件常见于：一个"框架页"（只有筛选条件，无数据）+ 若干 `.files/` 下的分页文件。框架页 → `辅助文件-无数据`。

**(d) `.pdf`**

按顺序尝试，任一成功即止：

1. 文件名 token 命中（§6）；
2. 同目录存在**同名** `.xls/.xlsx`，且该 Excel 已**唯一**定案 → 继承，但必须校验：源文件不是多账户、PDF 修改时间不早于 Excel、文件名中的期间一致；
3. PDF 文本层抽取：用标准库 `zlib` 解 `FlateDecode` 流，抓 `Tj/TJ` 中的字符串，拼成文本后找 ≥8 位数字，与账户比对；
4. 全部失败 → `待确认-PDF无文本层`。

> 不要承诺 OCR。v1 的 `historydetail455.pdf` 属于扫描件，v2 的处理就是"进待确认，人工打开首页登记"。

### 7.4 多账户文件

满足任一条件即判定为多账户，**每个账户输出一行**（同一文件重复出现在多行）：

- "本方账号"列出现 ≥ 2 个不同值；
- 文件里存在"账户清单区块"（如筛选条件 `Account: 'Equals' 111,222,333`），区块内 ≥ 2 个账号；
- 文件名含 ≥ 2 个命中清单的 token。

状态记 `已匹配-多账户`，置信度 高。清单内找不到的账号单独进 `有流水无账`。

## 8. 状态与置信度

| 状态 | 含义 | 置信度 |
|---|---|---|
| `已匹配-文件名+内容一致` | 文件名和内容指向同一账户 | 高 |
| `已匹配-内容` | 表头字段直取，唯一命中 | 高 |
| `已匹配-多账户` | 一文件多账户，已拆行 | 高 |
| `已匹配-文件名` | 仅文件名证据，内容无法校验 | 中 |
| `已匹配-同源PDF` | 继承同名 Excel | 中 |
| `待确认-文件名多候选` | 文件名命中多个账户且无法唯一化 | — |
| `待确认-证据冲突` | 文件名与内容的账号不一致 | — |
| `待确认-无本方字段` | 只有对方账号/无账号字段 | — |
| `待确认-PDF无文本层` | 扫描件 | — |
| `待确认-加密` | 加密或损坏 | — |
| `无匹配-账号不在清单` | 抽到了本方账号，但清单没有 | — |
| `辅助文件-无数据` | HTML 框架页/空表/`.files` 碎片 | — |

**硬性要求：`待确认-*` 与 `无匹配-*` 必须逐条给出"人下一步该看什么"**（打开哪个文件、看哪个 sheet 哪一行、对比哪个值）。

## 9. 双向差异与去重

### 9.1 双向差异

- **有账无流水**：清单里没被任何文件命中的账户。**必须分三桶**：非零余额（真嫌疑）/ 零余额 / 已销户。v1 只加了一句备注，统计上没分开，会误导。
- **有流水无账**：文件里抽到的账号不在清单。按账号去重统计，但**保留文件明细**（一个账号可能出现在多个文件里）。

### 9.2 去重

- **完全重复**：`sha1(文件字节)` 相同 → 标 `重复件`，仍需在明细里逐文件列示（审计要求可追溯），但**汇总金额时必须排除**。
- **期间重叠**：同一账户的多个文件，若交易日期区间有交集 → 标 `期间重叠`，并给出重叠起止日。**这比 MD5 重要得多**，是二期做金额核对时重复计算的主要来源。

## 10. 输出规范

产出 **1 个 xlsx（7 张表）+ 1 个 jsonl（逐文件证据，供回归比对）**，放在流水目录同级。

### 10.1 表 1 `说明`

运行参数（输入目录、清单文件名、时间戳、程序版本）、样本量、各状态计数、**统计勾稽行**（见 §10.8）、口径声明（本表只做账户归属，不含金额核对）。

### 10.2 表 2 `匹配明细`（核心）

| 列 | 内容 |
|---|---|
| A | 序号 |
| B | 文件名（相对路径） |
| C | 实际格式（xlsx / xls_biff8 / html / pdf / encrypted） |
| D | 大小(KB) |
| E | 内容指纹 sha1 |
| F | **匹配依据**（文件名 / 内容-表头字段 / 内容-区块 / 同源PDF / 多账户拆分 / 无） |
| G | **证据位置**（`文件名` / `Sheet「账户明细」!C5` / `PDF 第3页` / `-`） |
| H | **证据表头原文**（如 `本方账号`；文件名证据留空） |
| I | **命中值（原始）** |
| J | 归一化账号（digits） |
| K | 置信度（高/中/低） |
| L | 账户名称（清单） |
| M | 账号（清单，文本格式） |
| N | 开户银行（清单） |
| O | 币种 |
| P | 匹配状态（§8） |
| Q | 交叉校验（一致 / 冲突：文件名=X 内容=Y / 未校验） |
| R | 备注（重复件、期间重叠、多候选说明、尾号不符等） |
| S | 打开文件（相对超链接，`HYPERLINK` 到 B 列路径） |

**F/G/H/I 四列是本任务的存在意义**，缺任何一列都视为未完成。

### 10.3 表 3 `账户全覆盖`

清单每一行都出现（含零余额/已销户）：`序号 | 公司 | 账号 | 银行 | 币种 | 余额 | 命中文件数 | 命中文件列表 | 覆盖状态 | 备注`。

### 10.4 表 4 `有账无流水`

字段同表 3 的子集，**按三桶分段**（非零余额 / 零余额 / 已销户），非零余额排最前。

### 10.5 表 5 `有流水无账`

`序号 | 抽到的账号 | 来源文件 | 证据位置 | 备注`。

### 10.6 表 6 `冲突与待确认`

`序号 | 文件 | 类型（冲突/多候选/无字段/PDF/加密） | 候选A | 候选B | 建议人工动作`。

### 10.7 表 7 `重复与重叠`

`sha1 | 份数 | 文件列表 | 是否期间重叠 | 重叠区间`。

### 10.8 统计勾稽（必须能对平）

```
文件总数 = Σ 各状态文件数
账户总数 = 有流水账户数 + 有账无流水账户数
明细行数 = Σ 每个文件的账户数（多账户文件贡献多行）
明细行数 ≠ 文件总数，差值必须等于"多账户拆分产生的额外行数"
```

表 1 里必须出现这四行。v1 的数字（207 / 159 / 195 / 84 / 75）之间没有任何交叉校验，出错看不出来。

### 10.9 jsonl 侧车

每文件一条：

```json
{"file":"...","format":"xls_biff8","evidences":[{"source":"content_header","location":"Sheet1!C5","label":"本方账号","value_raw":"755932641710201"}],"account":"755932641710201","confidence":"高","status":"已匹配-内容","check":"一致"}
```

用途：改一次适配器，diff 一次 jsonl，逐文件证明"只有预期的那几条变了"。

## 12. 与 v1 结果数字的差异是预期的

v2 跑出来的"已匹配"数量**大概率低于** v1 的 195，这是**正确**的，因为 v1 的位置启发式把一部分"有流水无账"错判成了"已匹配"。

**验收方式不是"数字对得上 v1"，而是**：把 v1 的匹配明细与 v2 的逐行 diff，对**每一条差异**给出解释，归入以下三类之一：

1. v1 假匹配，v2 纠正（对应 §3.1 / §3.3 那几条）；
2. v1 漏匹配，v2 补上（对应短号/分行号/前导 0 的双向匹配）；
3. 无法解释 → **视为 v2 的 bug**。

## 13. 实现环境要求

- Python 3.10+，**只用标准库 + openpyxl**。
- 若环境里有 `pandas` / `xlrd` / `pdfplumber`，可以用，但**不得因此改变 §3 的判定逻辑**（例如不能把"读不到"变成"猜一个"）。
- 不依赖本机 Excel / Office / COM。
- 路径处理统一 `pathlib`，脚本不得写死绝对路径；输入输出都从命令行参数或配置文件读。
- 全程不修改、不移动、不删除原始流水文件（只读）。
- 单进程即可；207 份文件应在 2 分钟内跑完。

## 15. 附录：v1 与 v2 对照

| 环节 | v1 | v2 |
|---|---|---|
| 文件名匹配 | 去非数字后子串包含 | token 化 + 双向后缀 + 长度差分档 + 唯一性裁决 |
| 多候选 | 全部记为匹配（一文件多账号） | 最长优先；仍不唯一则待确认 |
| 内容匹配定位 | 只说"内容识别" | 必记 sheet + 单元格 + 表头原文 |
| 取不到本方账号 | 取最早出现的清单账号 | 待确认，不定案 |
| 一列多值 | 取众数 | 判定多账户，拆行 |
| `.xls` | 字节流扫描 | OLE2 + BIFF8 结构化解析 |
| 交叉校验 | 无 | 文件名 vs 内容，冲突必报 |
| 去重 | MD5 | sha1 标完全重复 + 交易指纹标期间重叠 |
| 统计 | 无勾稽 | 四行勾稽必须对平 |
| 可复现 | 不可（启发式） | 可（纯规则 + jsonl 逐文件证据） |

# 设计稿 · 判断留痕（_judgments）与黄格分诊

> 状态：**第 1 步已落地**（见 `V1.2.09_判断留痕数据层.md`）；第 2~4 步待做。
> 目的：把「AI 判断并留痕」从口号变成可校验的数据结构，并让底稿里上百个黄格子各自带着处置办法。
> 范围：横切三个板块，不改任何现有输出口径。第 1 步落地时平台行为零变化。

---

## 一、一页结论

现在平台有两条腿，一条很硬，一条是空的：

| | 工具层（写死规则） | AI 层（判断） |
|---|---|---|
| 现状 | 有代码、有测试、错不了 | 只有提示词，往外发完就断了 |
| 可验证性 | 21 条断言能抓 | 结论对错、依据有无，平台一概不知 |
| 产物 | xlsx 单元格 | 无 |

审计的底线是「结论要有依据」。所以 AI 层缺的不是更聪明的提示词，是**一个能存住「值 + 依据 + 谁定的 + 复核没有」的落点**。

同时，现在每个空白格都只标黄 + 一句「需人工判断」。162 行的 BKD 生成出来，人面对的是几十到上百个黄格子，没有分诊就等于没有清单。而这批黄格子其实只有四种成因，其中两种根本不该人工填。

**这一版做三件事**：

1. 建 `_judgments` 表 —— 一个判断一条记录，键是「主体 + 科目 + 账户 + 期间 + 字段」，可跨期继承、可复核、可导出。
2. 把 `_fill_bkd` 里那串 if-else 抽成 `resolve()` 六级优先级 —— 判断从「写死在代码里」变成「查表得出」。
3. gap 加 `class` 字段（A/B/C/D）—— 让「标黄」分出「AI 该判的 / 去追客户的 / 自己配错的」。

**不做的**：AI 不自动落笔（最高只能到 draft）；不跨主体套用判断；不做全局判断库（判断属于账套）。

---

## 二、概念分层：症状、处方、成因

三个概念现在混在一起，必须拆开：

- **gap（症状）**：本次生成时发现的一个空白或待判格子。它是「当前数据状态的函数」，随时可重算，不持久化。
- **cause（成因）**：这个格子为什么空。这是 `recon._check_aux` 已经在算的五态，应该推广到所有 gap。
- **judgment（处方）**：针对某个点位给出的值 + 依据 + 状态。持久化，跨期复用。

关系：`gap = (位置, 字段, 成因)`，`judgment = (位置, 字段, 值, 依据, 状态)`。gap 靠 judgment 消解；消解不了的，按成因变成待办或修复链接。

### gap 四分类

| 类 | 名称 | 判据 | 处置 | 标色 | 入库 |
|---|---|---|---|---|---|
| **A** | 能定 | `_judgments` 有 confirmed 值；或命中写死规则（银行存款函证=是）；或上年底稿回捞到 | 直接填，Notes 注来源 | 不标 | judgment（已有） |
| **B** | 缺料 | 源表**没有这一列**，且该字段不是准则判断项（账号、开户行、费用类别） | 生成待办，去追客户 | 黄 | `_todos` |
| **C** | 待判 | 该字段是准则/职业判断项（受限性质、其他货币资金是否函证、OAR 结论、抽样结论） | AI 起草 → 人工确认 | 黄 | judgment(status=draft) |
| **D** | 配错 | 源表**有列**，但映射没配 / 合并后为空（清洗误删） | 一键跳修复，不用重导 | 橙 | 不入库 |

D 类是本设计最省时间的一类：映射漏配改一下就行，却被当成「缺资料」发给客户，这是纯粹的内耗。

## 三、表设计

### 3.1 `_judgments`（核心）

```sql
CREATE TABLE IF NOT EXISTS _judgments(
  jid         VARCHAR PRIMARY KEY,   -- md5(scope|entity|subject|dim_type|dim_key|period|field)[:16]
  scope       VARCHAR,               -- 取数域: bkd.c00 / bkd.exp / wp.g3 / oar / cutoff
  entity      VARCHAR,               -- 主体（company_name，与 BKD 同口径）
  subject     VARCHAR,               -- 一级科目（银行存款 / 其他货币资金 / 预付账款…）
  dim_type    VARCHAR,               -- acct(账号) / vendor(供应商) / item(OAR项目) / blank(科目级)
  dim_key     VARCHAR,               -- 归一后的账户键 / 供应商名 / 项目名；无维度为 ''
  period      VARCHAR,               -- YYYYMM；'' 表示跨期通用（继承用）
  field       VARCHAR,               -- nature / confirm / notes / oar_value / conclusion …
  value       VARCHAR,               -- 结论原文（直接写进单元格的字符串）
  source      VARCHAR,               -- rule / prior_bkd / prior_judgment / ai / human / calc
  basis       VARCHAR,               -- 依据。文件名+格号、AI 引用原文、人工备注
  confidence  DOUBLE,                -- 0~1，仅 ai 有；其余为 NULL
  status      VARCHAR,               -- draft / confirmed / rejected / expired
  run_id      VARCHAR,               -- 产生它的那次生成（可追溯到批次）
  created_by  VARCHAR, created_at TIMESTAMP,
  reviewed_by VARCHAR, reviewed_at TIMESTAMP
)
```

**为什么 jid 用业务键哈希而不是自增**：一张底稿重生成十次，同一格必须落在同一条记录上。自增 ID 每跑一次加一条，三个月后表里有 800 条重复判断，没人敢用。业务键哈希让写入天然变成 upsert（`INSERT OR REPLACE`）。

**为什么 `dim_type`/`dim_key` 而不是 `acct_no`**：G3 是供应商级、OAR 是项目级、C.00 是账户级。用 `acct_no` 建表，G3 就得再加一张表，然后两张表的复核逻辑各写一遍。

**账户键必须归一**：`dim_key` 走现有 `accounts._acct_norm_py`（全角转半角、去空格连字符、去前导零）。`7559-3264-1710-201` 和 `755932641710201` 是同一个账户，不能让客户改一次账号格式就丢一次判断。现金无账号，`dim_key=''`、`dim_type='blank'`。

**period 的通配语义**：查值时先精确匹配本期，再兜底 `period=''`。所以「这家公司所有账户一律函证」可以只写一条 `period=''`，新开账户自动继承；而「2026 年这户变成了保证金户」写 `period='202610'`，优先级更高。

### 3.2 `_todos`（缺料待办）

B 类 gap 需要状态机，不能只留在内存里。

```sql
CREATE TABLE IF NOT EXISTS _todos(
  tid        VARCHAR PRIMARY KEY,   -- md5(scope|entity|dim_key|field)[:16]
  scope      VARCHAR, entity VARCHAR, dim_key VARCHAR, field VARCHAR,
  title      VARCHAR,               -- 「甲公司 · 招商银行 7559*** · 开户行缺失」
  why        VARCHAR,               -- 成因原文（源表无此列 / 客户未填 / 上年为空）
  ask        VARCHAR,               -- 要客户补什么（可直接复制进邮件）
  affected   INTEGER,               -- 影响多少格（同一问题跨账户合并）
  status     VARCHAR,               -- open / asked / received / waived
  note       VARCHAR, updated_at TIMESTAMP
)
```

按 `(entity, dim_key, field)` 去重并把 `affected` 累加 —— 客户回一封邮件能补 8 个账户，待办应该是 1 条而不是 8 条。

`waived`（客户明确不提供）必须留痕：底稿要能回答「这一格为什么空」，答案不能是「忘了」。

### 3.3 两张表都存在账套主库里

跟随 `_recipes` / `_books`，由 `db._init()` 的 `CREATE TABLE IF NOT EXISTS` 建。判断属于这个账套的数据，换账套就没了 —— 这是对的。跨年新账套要复用的话，走导出 CSV 再导入，不做全局库（全局库会导致 A 客户的判断串到 B 客户，这类事故比省的那点操作严重得多）。

## 四、取值优先级（六级链条）

这是整个设计的核心规则，必须写死在一个函数里，任何科目都能用：

| 级 | 来源 | 条件 | 写进单元格 | 状态 |
|---|---|---|---|---|
| 1 | 本期人工确认 | `_judgments` 命中，status=confirmed，period=本期 | 值 | 不标黄，Notes 注「人工判断」 |
| 2 | 往期确认继承 | 命中 confirmed 且 period='' 或往期 | 值 | 不标黄，Notes 注「沿用 YYYYMM 判断」 |
| 3 | 上年底稿回捞 | 现有 `merge()` 的 `_matched` 命中 | 值 | 不标黄，Notes 注来源文件 |
| 4 | 平台规则 | 写死规则（银行存款函证=是） | 值 | 不标黄，检查表记「规则」 |
| 5 | AI 起草 | `_judgments` 命中 status=draft | 值 | **标黄**，批注写依据 + 置信度，等人确认 |
| 6 | 无 | 以上都没有 | 空 | 标黄 + 批注写「怎么办」 |

关键点：**第 5 级仍然标黄**。AI 起草的值写进格子是为了让人看着改，不是为了让它变成结论。这条不能松，否则「AI 判断并留痕」就退化成「AI 静默改数」。

第 4 级和第 5 级的顺序不能换：规则明确的事（准则要求银行存款必须函证）不该让 AI 再说一遍，说了反而增加复核量。

### resolve() 的签名

```python
def resolve(conn, scope, entity, subject, dim_type, dim_key, period, field, *,
            rules=None, prior_row=None, default=None):
    """按六级链条取一个值。返回 (value, meta)，
    meta = {source, basis, status, jid, confidence}
    value 为 None 表示六条都没命中，调用方负责标黄 + 分诊。"""
```

`rules` 传入该科目的写死规则表（`{"confirm": "是" if subject=="银行存款" else None}`），`prior_row` 是 `merge()` 已经匹配好的上年底稿行。现有 `_fill_bkd` 里那段 if-else 全部退化成「准备参数 + 调 resolve + 按 meta 决定标不标黄」。

## 五、写入点与读取点

不做大改，只在四个位置插桩：

| 位置 | 现在 | 改成 |
|---|---|---|
| `bkd/core.py::_fill_bkd` 判断列循环 | `if/elif` 堆叠，`gaps.append` | 逐字段调 `resolve()`；据 meta 决定写值/标黄/生成 gap |
| `bkd/core.py::merge` | 回捞结果放 `row["_matched"]` | 顺手把回捞值落一条 `source=prior_bkd, status=confirmed`（回捞本身就是一种已确认依据） |
| `bkd/routes.py::_run_c00` | 返回 `gaps` 计数 | 返回 `gaps` 明细含 `class`；调 `_todos.sync()` 合并缺料项 |
| 新增 `core/judge.py` | — | `resolve / upsert / confirm / reject / inherit / export` 六个函数，纯数据层，不碰 xlsx |

`core/judge.py` 独立成文件而不是塞进 `bkd/core.py`（那已经 2500+ 行）—— 这是横切能力，费用和 G3 都要用。

## 六、gap 分诊规则

### 6.1 判定函数

```python
JUDGE_FIELDS = {"nature", "confirm", "oar_value", "conclusion", "sample_pick"}

def classify_gap(g, cause, has_col, all_blank, has_judgment):
    if has_judgment:                      return "A"   # 已有结论，不该出 gap
    if cause in ("not_mapped", "lost"):   return "D"   # 自己配错
    if has_col and all_blank:             return "B"   # 客户没填
    if not has_col:
        return "C" if g["field_key"] in JUDGE_FIELDS else "B"
    return "C"
```

`cause` 从哪来：直接复用 `recon._aux_origin()` 的五态，映射关系

```
present      -> A   辅助核算可用
never_present-> B   原始数据就没这维度 → 追客户
never_filled -> B   有列客户没填     → 追客户
not_mapped   -> D   映射漏配         → 自己改
lost         -> D   清洗误删         → 查留痕
```

这是本设计里最实的一处打通：**第五组检查的成因判定，直接决定 BKD 那堆黄格子里有多少根本不用问客户**。现在这两块是各算各的 —— 检查表说「映射漏配，可立即修复」，BKD 表说「源表未提供银行名称」，同一件事两个说法，用户只能两边猜。

### 6.2 落到 C.00 的实测映射

按当前代码，货币资金的黄格子会这样分：

| 字段 | 典型成因 | 类 | 处置 |
|---|---|---|---|
| 性质/用途 | 无数据源，准则判断（受限/非受限） | C | AI 读附注起草，人确认 |
| 是否函证（银行存款） | 准则要求 | A | 规则命中，不再标黄 |
| 是否函证（其他货币资金） | 要判是不是银行账户 | C | AI 起草 |
| 银行/存款机构 | 核算维度为空 | B/D | 先看第五组成因，D 就直接改映射 |
| 账号 | 同上 | B/D | 同上 |
| Notes | 模板公式 | A | 不动 |

## 七、AI 层契约

平台不能只发提示词。要收结构化结果，否则「留痕」无从谈起。

**`GET /api/judge/plan?scope=bkd.c00`** 返回待判清单：

```json
{"items": [{"jid": "...", "entity": "甲公司", "subject": "其他货币资金",
            "dim_key": "7559...", "field": "confirm",
            "question": "该账户是否为银行账户？是否函证？",
            "enum": ["是", "否"], "context": "摘要中出现「保证金」…"}],
 "count": 23}
```

**`POST /api/judge/apply`** 收 AI 结果，逐条校验后才入库：

```json
{"items": [{"jid": "...", "value": "否", "basis": "附注五(二)：保证金存款 300 万，受限",
            "confidence": 0.86}]}
```

校验四条，不合格整条打回（不静默丢弃）：
1. `jid` 必须存在于本次 plan（防止 AI 编造点位）
2. `value` 必须在 `enum` 内（防止自由发挥）
3. `basis` 非空且 ≥ 8 字（防止「根据经验判断」这种空话）
4. `confidence < 0.6` 的直接标「证据不足」不写值

入库一律 `status=draft, source=ai`。**AI 没有 confirmed 权限，接口层面就不给**。

前端两个键：「复制提示词」（带 plan 的 json）和「粘贴结果」。这样任何 AI（包括别的模型、包括人工手写）都能填，平台不绑定某一家。

## 八、界面落点

三处，都不新增页面：

1. **一键上数预览**：tiles 从「标黄 87 格」变成「A 可定 41 / B 缺料 23 / C 待判 19 / D 配错 4」，点击任一数字跳到对应清单。
2. **待确认清单**：现有 `renderGaps` 加分类标签和处置按钮 —— B 类给「复制追问清单」，C 类给「AI 起草」，D 类给「去改映射」（跳清洗页并带上 sid）。
3. **判断留痕面板**（新增折叠区）：列出本账套所有 judgment，按状态筛选，confirmed 的可改可撤。这是复核人真正会看的东西。

## 九、底稿怎么写

单元格
- C 类且 draft：值写进去 + 黄底 + 批注「AI 起草（0.86）：附注五(二)…，待复核」
- B 类空：黄底 + 批注写**要什么**（「请客户提供该账户开户行名称」），不写「无数据源」

检查表新增「判断留痕」区块（在现有待确认清单之前）：

| 位置 | 字段 | 值 | 来源 | 依据 | 状态 | 复核人 |
|---|---|---|---|---|---|---|
| C.00 BKD!H12 | 是否函证 | 否 | AI | 附注五(二)：保证金… | 待确认 | |
| C.00 BKD!H15 | 是否函证 | 是 | 规则 | 银行存款一律函证 | 已定 | 平台 |

这张表是这一版真正的交付物 —— 它让复核从「再算一遍」变成「看依据」。

## 十、迁移四步（每步都可停）

| 步 | 改动 | 风险 | 验证 |
|---|---|---|---|
| 1 | 建两张表 + `core/judge.py` + 三个 API。`_fill_bkd` 不动 | 无（只加不减） | 生成结果逐格不变 |
| 2 | `_fill_bkd` 的判断列换成 `resolve()` | 中 | 改前改后 xlsx 逐格比对，除新增区块外零差异 |
| 3 | gap 加 `class`，前端分诊 | 低 | 分类总数 = 原 gaps 总数 |
| 4 | AI 起草闭环 | 低 | apply 校验的四条各造一个反例 |

**第 2 步的零变化证明**如何做（这是允许改既有代码的前提）：用 `tmp/_e2edata` 跑两次生成，改前存 baseline，改后存新版，用 openpyxl 遍历所有 sheet 所有已用格，跳过「检查」表新增区块，断言 `(值, 底色)` 完全相等。现有 `test_c00.py` 和 `test_wp_e2e.py` 保证业务数字不变，逐格比对保证格式不变。

第 2 步做完先停一轮，等测试反馈再上第 4 步。判断链一旦跑通，加科目就只剩填规则表。

## 十一、验收标准

1. 同一张底稿连生成三次，`_judgments` 行数不增长（幂等）。
2. 人工确认一条判断后重生成，该格不再标黄，Notes 含「人工判断」。
3. 下期生成（period 变），上期 confirmed 的值自动继承，Notes 含「沿用 202610」。
4. 账号写成 `7559-3264-1710-201` 与 `755932641710201` 命中同一条 judgment。
5. AI apply 一条 `enum` 外的值 → 返回 400 并说明是第几条、哪个字段。
6. AI apply 一条 `basis` 为空 → 同上。
7. 所有 gap 的 A+B+C+D = 原 gap 总数，且 D 类点击能跳到正确 sid。
8. 第 2 步的逐格比对报告：除新增区块外零差异。

## 十二、明确不做

- **AI 自动确认**：接口层不给。这是与外部 v2 文档「C 级只准备不落笔」一致的硬边界。
- **跨主体借用判断**：同集团不同主体的账户性质可能相反（一个受限一个不），串用是事故。
- **判断库上云/全局**：先按账套。等有 3 个以上客户反复用同一套判断时再说。
- **自动调和差额**：现有铁律不变 —— 差额必须解释，禁止 ROUND/+1 调平。judgment 只存判断，不存调平手法。
- **G3**：这一版不动科目，只铺底座。G3 的价值恰恰在于验证这套底座能不能撑住「供应商级 + 账龄桶」，所以底座先稳。

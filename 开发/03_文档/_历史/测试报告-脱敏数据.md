## P0 — 严重（直接导致结果错误）

### P0-1 多账簿 TB 的主体列未被自动识别，16 家公司混成一个主体
- 现象：TB 的账簿信息在「方案层级」列（值如 `1A公司(100)`、`9H公司(107)`、`多账簿(01)`），自动映射没有把任何列映射到「账簿名称/公司名称」。
- 后果：merge 后 `tb` 表的 `book_name`、`company_name` 全为空；`/api/tb` 取数返回 3 条记录且 `company` 全空；BKD 生成时 `matched=0`（上年 BKD 的 2 个账户一个都匹配不上，全部判为「缺失」）。
- 附：mapping 表里其实有 `1A公司(100)→A公司` 等 52 条映射，JE 已正确回填（matched 56704），但 TB 因没有账簿列而完全无法回填。

### P0-2 TB 的「合计」行、「多账簿(01)」汇总行、父级科目行未被清洗，金额重复计算
- 现象：默认预设清洗里「删除合计行」只按「科目名称」列匹配关键词「合计」，但本数据的「合计」在「核算维度名称」列、「多账簿(01)」汇总在「方案层级」列，均不命中。
- 定量证据（1002 银行存款）：
  - 账号明细行期末余额(借) 之和 = 89.77 亿
  - 合计行期末余额(借) 之和 = 89.77 亿（与明细完全重复）
  - 多账簿汇总行 = 14.23 亿
  - 三者相加 = 193.76 亿 ← 这正是 BKD 里显示的银行存款金额
- 正确本币余额应为 14.23 亿（综合本位币口径）。
- 同类问题：库存现金正确 416.9，BKD 显示 1313.8（重复 3 倍）；其他货币资金正确约 4.7 亿，BKD 显示 7.05 亿。

### P0-3 JE 的「合计」总计行（账簿列 =「合计」）未被清洗，序时账发生额翻倍
- 现象：JE 最后一行（`_src_row=56706`）账簿=`合计`，只有金额（借方 346 亿、贷方 308 亿），其余全空。预设清洗未删除它。
- 定量证据：
  - JE 借方发生额含合计行 = 692 亿；不含 = 346 亿（**正好翻倍**）
  - JE 贷方发生额含合计行 = 617 亿；不含 = 308 亿
- 该行也被 `journal-probe` 记为 `badDate=1`。

### P0-4 多币别 TB 的「本币 / 原币」列识别错乱
- 现象：SAP 导出的金额列是「期初余额(借)」=原币、「期初本位币(借)」=本位币。自动映射把「期初余额(借)」当成本币 `open_debit`，而「期初本位币(借)」没有任何规则识别，被丢弃。
- 后果：`/api/tb` 取数里 `orig == local`，外币账户的本币金额用了原币数值，金额错误；且本币列数据彻底丢失。
- 根因：`FX_HINT` 只认「外币/原币/外汇/美元/港币…」，不认「本位币」；`TB_RULES` 也没有「本位币」这一认词。

### P0-5 「综合本位币」行与各具体币别行未区分，同一账户金额被重复加总
- 现象：TB 每个公司×账号有「综合本位币」汇总行 + 美元/欧元/日元…各币别明细行。两者是父子关系，但取数时全部加总。
- 后果：本币金额重复（综合本位币 14.23 亿 + 各币别折算 14.23 亿 = 28.4 亿，再叠加合计行/汇总行进一步放大）。

## P1 — 中等（影响部分功能或需人工干预）

### P1-1 currency 自动映射缺「币别」关键词
- JE 和 TB 的币别列都叫「币别」，但匹配规则只认「币种/货币/currency」，导致 currency 无法自动识别（需手工映射）。

### P1-2 JE 的 bank_account 映射到了「编码」列而非「名称」列
- JE 有 `核算维度.银行账号.编码`（值「账号130」）和 `核算维度.银行账号.名称`（值「A公司」等，脱敏后为账户名）。自动映射把 `bank_account` 指到了编码列。
- 后果：cutoff 抓数时 `payAcct/recvAcct` 全空，提示「付款账号未识别；对方账号未识别」；BKD 里银行账号显示为「账号130」而非银行账户名。

### P1-3 is_money_account 误判（名称包含关键字）
- `6603.01.01 财务费用_利息收入_银行存款` 因名称包含「银行存款」被判定为货币资金账户（journal-probe 标 `money:true`）。
- 后果：财务费用科目（1215 行）被误纳入货币资金取数范围。

### P1-4 TB 的银行账号维度（核算维度编码/名称）未自动识别
- TB 的银行账号在「核算维度编码/核算维度名称」两列，但列名不含「账号/银行」等词，自动映射识别不出 `bank_account`。
- 后果：BKD 无法按账号维度拆户、无法与上年 BKD 的账号匹配。

### P1-5 账簿对照表导入不自动识别标准列
- `主体mapping表` 的列名就是「账簿名称/公司名称」，但 `/api/books/import` 不传 book_col/company_col 时直接报「必须指定账簿名称是哪一列」，需手工指定。

## P2 — 低（边界 / 可用性 / 需确认口径）

### P2-1 负金额（红字冲销）未处理
- JE 借方金额为负 1120 行、贷方为负 96 行；`6603.01.01` 财务费用的借/贷全为负数。
- 直接求和会抵减发生额，核对/BKD/cutoff 的金额口径需要明确（红字借方应冲减借方还是并入贷方）。

### P2-2 未审核凭证未提示
- JE 审核状态有「创建」4807 行（未审核）、「重新审核」1 行。当前无任何过滤或提示，是否应排除需确认审计口径。

### P2-3 空币别行未清洗
- TB 1001 库存现金存在「美元/欧元/人民币」等无金额的空币别行，未被清洗，增加噪音。

### P2-4 核对强依赖「一级科目」列
- 单级科目编码（如 1002）也必须先手动加「提取一级科目/生成一级科目」步骤并映射 `acct_l1`，否则核对直接报错。这是设计约束，但对单级编码数据体验较差。

## 测试结论与建议

1. 上述 P0 问题集中在**「多账簿 + 多币别」**这一场景，而脱敏数据恰好是真实的 SAP 多账簿、多币别导出。当前版本对「单账簿、单币别、人民币」的账套是够用的，但一旦出现多账簿/外币，金额就会错。
2. 优先修复顺序建议：P0-2/P0-3（合计/汇总行清洗）→ P0-1（主体识别）→ P0-4/P0-5（本币/原币、币别维度）→ P1 各项。
3. 本报告只描述问题，未改动任何代码。测试期间程序代码与主目录逐字节一致，仅新增了测试数据目录 `data_test`、测试脚本 `tmp/hc.py`、上年 BKD 样例等测试产物（均在归档 zip 内）。

> 来源：`03_文档/V1.2.09设计_判断留痕与黄格分诊.md` 设计稿的第 1 步落地
> 改动文件：`core/judge.py`（新增）、`core/db.py`、`modules/bkd/routes.py`

本步只加数据层与接口，**不动 `_fill_bkd`**，所以底稿生成结果必须逐格不变。

## 1. 两张表

```sql
_judgments(jid PK, scope, entity, subject, dim_type, dim_key, period, field,
           value, source, basis, confidence, status, run_id,
           created_by, created_at, reviewed_by, reviewed_at)
_todos(tid PK, scope, entity, dim_type, dim_key, field,
       title, why, ask, affected, status, note, updated_at)
```

由 `db._init()` 建（换账套自动重建），`judge.ensure()` 兜底。

**主键用业务键哈希**：`md5(scope|entity|subject|dim_type|dim_key|period|field)[:16]`。
一张底稿重生成十次，同一个格子必须落在同一条上。自增 ID 跑三个月就是几百条重复判断。

**`dim_type`/`dim_key` 而不是 `acct_no`**：货币资金是账户级、G3 是供应商级、OAR 是项目级，
用账号建表 G3 就得再建一张。

**两个写死的边界**：

- 只有「人工」和「AI」的判断入库。规则命中、上年底稿回捞每次实时算 —— 它们可复现，
  入库只会制造「改了规则却被旧缓存压住」的不一致。
- AI 起草不能覆盖已确认的人工结论（`upsert` 拦截，返回「如需修改请人工确认」）。

## 2. 取值六级链条（`judge.resolve()`）

```
1 本期人工确认 → 2 往期确认继承 → 3 上年底稿回捞 → 4 平台写死规则
→ 5 AI 起草（仍然标黄） → 6 空
```

三处不能换顺序：

- **规则排在 AI 之前**。银行存款一律函证是准则要求，让 AI 再说一遍只增加复核量。
- **AI 起草排在最后**，且 `is_draft()` 为真时调用方必须继续标黄 —— 写进格子是为了让人看着改，
  不是让它变成结论。
- **往期继承排在回捞之前**。人工确认过的判断比上年底稿的原值权威。

`period` 的通配语义：查值先精确匹配本期，再找最近一期，最后兜底 `period=''`（跨期通用）。
所以「这家公司所有账户一律函证」写一条通用的，明年新开账户自动继承；
「2026 年这户变成保证金户」写 `202610`，压过通用值。

## 3. 分诊（`judge.classify_gap()`）

| 类 | 判据 | 处置 | 标色 |
|---|---|---|---|
| A | `confirmed` 判断 / 规则 / 回捞 | 直接填，Notes 注来源 | 不标 |
| B | 源表缺这一列，且不是职业判断项 | 生成待办，去追客户 | 黄 |
| C | 职业判断项（性质、函证、结论） | AI 起草 → 人工确认 | 黄 |
| D | 映射漏配 / 清洗误删 | 一键跳修复，不用重导 | 橙 |

判定顺序是 A → D → C → B：**D 必须排在 B 之前**。映射漏配被当成「缺资料」发给客户，
是纯内耗；现在每个 D 类 gap 的提示直接写「改配置即可，不用重导」。

**AI 起草（draft）不算 A 类**。这一点在测试里专门抓过一遍：最初实现把 draft 也标成
`resolved=True`，结果 AI 一落草案就当成了定论，正是设计里明令禁止的事。

## 4. 七个接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/judge/plan` | 实时跑 C.00 预览 → 黄格分诊 → C 类列成待判清单 |
| POST | `/api/judge/apply` | 收 AI 起草结果，四条校验后落 `draft` |
| POST | `/api/judge/save` | 人工直填，即 `confirmed` |
| POST | `/api/judge/review` | 确认 / 驳回（AI 起草必须过这一步） |
| GET | `/api/judge/list` | 判断清单 + 统计 |
| GET/POST | `/api/judge/todos` · `/todos/sync` · `/todo` | 缺料待办：合并、推进状态 |

`apply` 的四条校验，不合格整条打回并说明「第几条、哪个字段」，**不静默丢弃**
（静默丢弃会让 AI 以为自己写进去了）：

1. `jid` 必须是 16 位 hex，且在本次 plan 发出的点位集合内（防编造位置，缓存 1 小时）
2. `value` 必须在字段枚举内（如是否函证只能是 是/否）
3. `basis` ≥ 8 字（挡住「根据经验判断」这类空话）
4. `confidence < 0.6` 不写值（证据不足）

| 测试 | 结果 |
|---|---|
| `tmp/test_judge.py`（纯数据层，40 条断言） | 40/40 |
| `tmp/test_judge_api.py`（接口，25 条断言） | 25/25 |
| `tmp/test_wp_e2e.py` | 9 行 / 12,215,000.00 / OAR 12,215 千元勾稽平，**与改前一致** |
| `test_t01_t08` / `test_c00` / `test_fx` / `test_cur` / `test_aux` / `test_flow` / `test_link` / `test_exp` | 全部 exit=0，test_fx 21/21 不变 |

重点覆盖的行为：

- 同键写三次只有一条（重生成不膨胀）
- 账号 `7559-3264-1710-201` / `755932641710201` / 全角写法归一为同一 `jid`；供应商名不被账号归一污染
- 下期自动继承上期判断，Notes 写「沿用 202610」
- 规则压过 AI；AI 的值仍标黄且带置信度
- AI 不能写 `confirmed`，也不能覆盖已确认结论
- 驳回后不再命中，回到空继续标黄
- 待办：同一问题跨账户合并 `affected` 累加；已 `received` 的不被重生成复活

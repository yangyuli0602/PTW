# V1.2.10 · 导入清洗 bug 排查修复

> 起因：对「数据导入清洗」做攻击性测试（而不是跑既有用例），在入口解析、清洗动作、
> 流水线三个层面各找到一批问题。本版修复 7 处，其中 2 处会直接算错数。
> 上数（BKD/OAR）代码未改动。

---

## 一、必读：两处会算错数的问题

### 1. 「删除小计行」把明细删光、只留合计（`clean._b_drop_subtotal`）

`run()` 里所有 filter 类动作的 `cond` 是**保留条件**（`CREATE TABLE AS SELECT … WHERE cond`），
而 `_b_drop_subtotal` 返回的是「命中合计」的条件，少了一个 `NOT`。结果点一次
「删除小计行」= 只保留合计行、删掉全部明细。

默认预设没用这个动作（预设用的是「按关键词删行」），所以日常导入不会踩到；
但用户手动加这个动作就会一次性毁掉整张表。

**修复**：条件改为 `NOT (…)`。

### 2. 「本年累计借方发生额」被映射成本期发生额（`fields.TB_RULES`）

`cur_debit` 的识别词里含「发生额」，`ytd_debit` 也含「本年」，两条规则对
「本年累计借方发生额」这个列名**同分**，最终按规则表顺序由 `cur_debit` 抢走。
后果：本年累计数被当成当期数，凡是用 ytd 的核对与底稿全错。

**修复**：`ytd_debit` / `ytd_credit` 的「本年/累计」概念权重 2 → 3。
「本期发生额借方」不带本年累计字样，仍归 `cur_*`（已回归）。

## 二、静默错值（不报错，但结果是错的）

### 3. 期间列是日期时没有归一（`db.MACROS._period_norm`）

原来只认 `2026-10` / `202610` / `10` 三种写法。以下写法**原样返回**，
导致同一期间被当成两个期间（数据检查的期间过滤、BKD 的期间筛选都会漏）：

| 输入 | 旧 | 新 |
|---|---|---|
| `2026年10月` | 原样 | `2026-10` |
| `2026-10-31` | 原样 | `2026-10` |
| `2026/10/31` | 原样 | `2026-10` |
| `2026年10月31日` | 原样 | `2026-10` |
| `20261031` | 原样 | `2026-10` |

同时加了两道闸，避免把别的编码当日期：

- 年份限定 `19xx / 20xx / 21xx`：科目编码 `1121.01.01` 不会被当成 1121 年 1 月；
- 8 位数字要求月、日在合法范围：流水号 `10537050` 不会被当成「1053 年 70 月」。

### 4. 文字里夹数字被当成金额（`db.MACROS._num`）

原来对解析不出标准写法的值会「去掉所有非数字字符再试」，于是
`合计123` → 123、`1A公司(100)` → 1100。这类值本来该是 NULL，静默取数
会让一个说明行/公司名参与金额汇总。

**修复**：只有当整串是「数字 + 千分位 + 货币符号 + 单位后缀（元/万元/美元/CR/DR/%）」
时才允许宽松解析，其余含文字的返回 NULL。

### 5. 表头重名仍可能撞车（`db.Ledger._header_names`）

列名是 `金额 / 金额_2 / 金额` 时，旧的计数式去重会生成两个 `金额_2`，
DuckDB 自动改名成 `金额_2_1` —— 用户在映射页看到的列名与实际入库列名对不上。

**修复**：改为「逐列检查，直到名字唯一为止」，结果恒为 `金额 / 金额_2 / 金额_3`。

### 6. 补前导零的位数不稳定（`clean._auto_len`）

`_auto_len` 取「出现次数最多的长度」，并列时没有次序。实测同一份数据
两次运行分别得到 4 和 10；取到 10 会把 `22` 补成 `0000000022`。
余额表里 4 位一级码和 10 位明细码并存是常态，所以这不是理论问题。

**修复**：并列时取**最短**长度（`ORDER BY c DESC, L ASC`）。

## 三、健壮性

### 7. 非法正则中断整条流水线（`clean._b_drop_keyword`）

正则模式下手填 `[`、`(abc`、`*`，DuckDB 执行期抛错 → `run()` break，
它后面的所有步骤都不再执行。用户看不出是「正则写错」，只看到「清洗没跑完」。

**修复**：构造阶段先用 Python `re` 预校验，不合法则该步降级为 noop，
提示「正则表达式无效（…）：xxx」，后续步骤继续执行。

顺带补了四个空列表保护（`drop_empty` / `drop_empty_key` / `drop_keyword` /
`drop_subtotal`）：表里只有 `_src_row` 时不再拼出空条件导致 SQL 语法错。

## 四、口径一致性

- **`drop_subtotal` 的匹配口径收严**：关键词必须出现在格子**开头或结尾**。
  原先子串匹配会把「管理费用—其他合计性支出」「结转本年合计支出」这类
  真实科目一起删掉。删错一行比漏删一行危险得多。
- **`audit.tb_subtotal` 同步同一口径**，并改掉那条会把用户引向误删的修复建议
  （原建议「加按关键词删行，关键词 合计,小计,总计」= 子串匹配）。
- **`AI提示词_清洗达标`（PROMPT）补一句判定口径**，防止 AI 用「包含」模式删除真科目。
  `03_文档/AI提示词_清洗达标.md` 已同步，`tmp/_mdcheck.py` 关键项 0 缺失。

## 五、测试基础设施（这次最值得留下的一笔）

排查中发现 **9 个离线测试里有 6 个没有 `sys.exit`** —— 断言失败也返回 0，
`regress.py` 只看退出码，所以此前显示的 PASS 只能说明「脚本没崩」。

修复：

1. `regress.py` 增加输出兜底 `looks_failed()`：退出码为 0 但输出含
   `✗` / `有不符` / `失败 N 项(N>0)` / `Traceback` 一律判 FAIL。
   已用 8 组正反样例验证不误伤（`40 项通过 / 0 项失败` 不判失败）。
2. `test_t01_t08` / `test_cur` / `test_link` 与四个新脚本补上退出码。
3. 没有断言的 `test_c00` / `test_flow` 从 PASS 改为 **CHECK（人工核验）**，
   不再冒充通过。
4. `test_judge_api` 改用每次运行独立的 scope —— 判断留痕的设计就是
   「同一点位跨期复用」，固定 scope 重复跑会继承上一轮结论，测试变成看脏数据。

新增四个攻击性测试，已纳入 `regress.py` 的离线组：

| 脚本 | 覆盖面 | 断言数 |
|---|---|---|
| `attack_clean.py` | 金额/期间解析、表头重名 | 27 |
| `attack_actions.py` | 正则、合计行、补零、向下填充、分隔符转义、去重、怪列名 | 24 |
| `attack_import.py` | 表头识别 6 例、余额表映射 8 组、序时账 4 组、流水 5 组 | 31 |
| `attack_run.py` | 留痕完整性、失败中断、临时表、upto、空表 | 11 |

## 七、影响面与注意事项

- **改了 `_num` / `_period_norm` 之后，已合并的 `tb` / `journal` 不会自动更新**
  （宏只影响此后执行）。如果之前合并过数据，请在「合并与检查」里重新生成标准表，
  期间与金额才会按新口径重算。
- 上数板块（C.00 / 费用 / OAR / 判断留痕）本版**未改动任何逻辑**。
- 折算率、`bkd_key`、父行递归判定等 V1.2.07 的口径不变。

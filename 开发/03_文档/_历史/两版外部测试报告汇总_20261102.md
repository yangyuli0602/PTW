## 0. 一页结论

两版共提出 **22 条**（去重后），我逐条核完：**21 条成立，1 条部分成立（条件性触发）**。

| 级别 | 条数 | 其中需立即修 |
|---|---:|---:|
| P0（静默给错结论 / 无法启动） | 3 | 3 |
| P1（假红、静默丢数、结果不可信） | 8 | 8 |
| P2（体验与可维护性） | 8 | 0（推广前） |
| P3（建议） | 3 | 0 |

**最危险的不是崩溃，是三条"静默出错"：**

1. **期间格式不兼容** —— 过滤成 0 行，然后输出几千条"仅余额表有"，用户会去查账而不是查工具。两版报告**独立撞到同一个坑**，只是格式不同（报告 1 撞 `1`~`12`，报告 2 撞 `2026年1期`）。
2. **`add_acct_path` 重复码删错行** —— 我实测：真实金额 500 的那行被删，留下 0 值占位行，**金额变 0 且无任何提示**。
3. **`add_acct_path` 数字父级不删** —— 我实测：父 1002（1000）+ 子 100201（600）+ 100202（400），结果合计 **2000**，正好翻倍。

**两版报告的数据互补，不是重复劳动**：报告 1 是多币种、大量凭证（245 万行）；报告 2 是单币种 + 中文期间 + 两行表头 + 父子同存。所以它们各自踩到对方没踩到的坑，合起来才把边界铺满。

## 3. 重点条目：实测证据

### U01 期间格式不兼容（P0，两版合并）

**两版撞的是同一处代码，不同格式。**

`core/recon.py:121-131` `_period_key()` 只对**纯数字**补零；`:134-137` `_pval()` 只对**1 位数字**补零。

实测四组（内存 DuckDB，直调 `_period_cond`）：

```
数据 1..12        + 输入 2026-01~06   →  0/12 行   ❌  （报告 1 的场景）
数据 1..12        + 输入 1~6          →  6/12 行   OK
数据 2026-01..12  + 输入 2026-01~06   →  6/12 行   OK
数据 2026-01..12  + 输入 1~6          →  0/12 行   ❌  （反向，报告 1 没发现）
数据 2026年1期..9期 + 输入 2026-01~09  →  0/3 行    ❌  （报告 2 的场景）
```

中文格式为什么必然失败（报告 2 说得对）：

```
'2026年1期' >= '2026-01'  → True
'2026年1期' <= '2026-09'  → False     ← '年'(U+5E74) > '-'(U+002D)，上界永远不成立
```

**两版都用同一个绕法逃过去了**（不映射 `period`，让 merge 从 `vdate` 派生 `YYYY-MM`）。这说明绕法是"行业惯例"，不是偶然——也说明这个坑一旦落到非技术用户手上就是死路。

**下游放大**：过滤成 0 行后，`_pair_check` 做 FULL OUTER JOIN，余额表侧全空 → 全部判"仅余额表有"。报告 1 的 1,461/6,369 条、报告 2 的"全量仅余额表有"都是这个机制。

### U02 合并缺列 500（P0，报告 2 新发现，我扩展了）

`core/db.py:1078 / 1082 / 1085-1090`。判据只查 `mapping.get(...)` 有没有值，**没有查 `_expr()` 的返回值**；`_expr()` 在列不存在时返回 `None`（`:1074` 有注释说明这是"降级成 NULL"的意图），于是：

```
COALESCE(_num("期初余额")::DECIMAL(20,2),0) - COALESCE(None,0) AS "open_bal_fx"
```

实测错误与报告一字不差：

```
Binder Error: Referenced column "None" not found in FROM clause!
```

**我多验证了一步**：报告只说了外币净额（`open_bal_fx`/`end_bal_fx`），但**本币的 `open_bal` / `end_bal` 是同一个模式**，同样会 500。实测：

```
映射 open_debit=有效列, open_credit=已删列  →  open_bal 也生成 COALESCE(...,0) - COALESCE(None,0)  →  同样的 Binder Error
```

所以修复时要覆盖 **4 个派生点**（open_bal / end_bal / open_bal_fx / end_bal_fx），不是 2 个。

顺带：`merge()` 的缺列 warning（`:1141-1147`）确实会算出缺列清单，但**算完只拼进文本，不阻止派生**，所以 warning 存在却仍然 500。

### U04 + U05 `add_acct_path`（P1，报告 2 新发现，实测最严重）

代码 `core/clean.py:290-297`：

```sql
leaf AS (
  SELECT _src_row FROM base s
  WHERE NOT EXISTS (SELECT 1 FROM base b2
    WHERE b2._entity = s._entity AND b2._code <> s._code
      AND starts_with(b2._code, s._code || %s))       -- ← U05：必须有分隔符
    AND NOT EXISTS (SELECT 1 FROM cnt c
      WHERE c._entity = s._entity AND c._code = s._code
        AND c._n >= 2 AND c._first = s._src_row))      -- ← U04：删"最靠前"而非"金额为 0"
```

我造的 5 行最小样本（父 1002 有金额，两个子 100201/100202；同码 1122 两行，第一行 500、第二行 0）：

```
原始 5 行 → 结果 4 行
1002     银行存款              1000   保留   ← U05：父行没被删
100201   银行存款_工行          600    保留
100202   银行存款_建行          400    保留   → 合计 2000（原始 1000，翻倍）

1122     应收账款_辅助核算未录入   0     保留   ← U04：留下的是 0 值占位行
被剔除：(src_row=4, 生成一级科目, 非末级科目行或合计数行)   ← 真实金额 500 那行被删
```

**U04 是本轮所有问题里风险最高的**：不报错、不进 warning、UI 上看不出，只有事后对不上账才会发现。报告 2 把它标 P1，我认为应该按 P0 对待。

### U06 + U07 单币种 FX 组 + 零金额单边（P1，报告 2 新发现）

代码 `core/recon.py:604-626`（jr 侧 FX UNION）、`:673-685`（status CASE）。

实测 1：单币种主体，TB 币别=综合本位币，JE 币别=人民币，本币金额完全相同。

```
total=2  bad=1  stats={'ok':1, 'bad':0, 'only_tb':0, 'only_jr':1}
  1001 / 人民币         tb=None  jr=None    → 仅序时账有   ← 假红
  1001 / 本位币（合计）  tb=200   jr=200     → 一致
```

实测 2：余额表只有 1001，序时账多一个 6602（借 500 贷 500，净额 0）。**一个科目产生 3 条假红**：

```
total=4  bad=3  stats={'ok':1, 'bad':0, 'only_tb':0, 'only_jr':3}
```

根因有两条，互相放大：

1. **币别范围**：jr 侧对所有币别生成组，没有 `WHERE currency IN (tb 的币别)`。国内单币种客户 TB 只有"综合本位币"、JE 只有"人民币"，于是每个科目都多出一组"仅序时账有"。
2. **豁免不对称**：`:674-677` 只对「仅余额表有 + 金额 0」判一致，`:673` 的「仅序时账有」**直接排在最前面，没有任何零金额豁免**。

报告 2 说 88 项假红，与"每科目 1–3 条"的量级吻合。

**这条对产品定位影响很大**：PTW 的典型客户是国内单币种企业，如果默认就跑出一屏红，第一次使用就会失去信任。

### U08 原币差列（P1，两版都提，比两版都严重）

两版都只说"列名易误读 / 缺脚注"。实际情况是**代码把它放进了 `diff_cols`，前端会标红**：

| 位置 | 内容 |
|---|---|
| `recon.py:373 / 396 / 454` | 第二组三个 part 都是 `"diff_cols": ["jr_diff", "jr_diff_fx"]` |
| `recon.py:311` | 第一组 `"diff_cols": [..., "tb_roll_diff_fx"]` |
| `recon.py:751` | 第三/四组 `"diff_cols": [..., "diff_debit_fx", "diff_credit_fx"]` |
| `app.js:2068` | `Math.abs(v) > tol` 就 `color:var(--danger);font-weight:600` |

结果：**同一行里 `status` 写"平衡"（绿），旁边原币差是红的**——自相矛盾的视觉信号。报告 2 说"第一组原币差最大 1.14 亿"，正好就是这种红。

（小修正：报告 2 把这列叫"本年累计借贷差(原币)"，实际第一组的原币列是 `tb_roll_diff_fx`「原币余额勾稽差」，第二组才是 `jr_diff_fx`「借贷差(原币)」。名称不准，问题本身成立。）

另外 `recon.py:328 / 374 / 464` 三处文案写「本币与原币同时核」，而判定里 `fx_ok = ""`（原币不参与）——文案与实现相反。

### U12 两行表头（P2，**部分成立**）

报告 2 说 `inspect` 返回 `header_row=4, header_rows=1`。我造了典型两行表头（第 4 行分类含合并单元格、第 5 行借/贷），**默认场景是能识别的**：

```
第5行前两格为空            → (4, 2)  正确
第5行前两格为空+金额说明    → (4, 2)  正确
第5行前两格重复上级文字     → (5, 1)  ❌ 第5行进数据
第5行只有借贷、无前导空列   → (5, 1)  ❌ 第5行进数据
```

根因在 `fields.py:495-502`：两层表头判定依赖"胜出行**左侧有空单元格**"（`lead_empty > 0`）。当导出把合并单元格拆开、前两列也写了文字，这个启发就失效。

所以：**不是"完全不支持两行表头"，而是"识别依赖一个脆弱的启发式"**。修法应该是加一条独立判据（下一行是否命中 `借方/贷方/期初/期末` 等词 ≥2 列），而不是只靠空格子数量。

### U16 期间 placeholder（P2）

`app.js:2165-2168` 用 `placeholder="2026-01"`，`2295` 取 `.value || ''` → 不填就是 `null` → **不过滤，扫全量**。用户看着框里有 `2026-01`，以为是默认值，实际是全期间。报告 2 说的"默认检查口径错"成立。

这条和 U01 是一对：一个让人以为填对了，一个填了也不对。

## 7. 我的建议（给你决策用）

**如果只做一件事**：做第一批的 **U01**。它一条就消掉两版报告里最大的一批假差异（报告 1 的 1,461+6,369、报告 2 的"全量单边"），而且改动局限在一个文件。

**如果做两件事**：加 **U04**。它是唯一会"静默把有金额的科目变成 0"的问题，其他问题最多是"多报"，它是"漏报"。

**如果要交给非技术用户试点**：第一批全部 + U06/U07/U16。否则国内单币种客户第一次跑就是满屏红。

**如果要定一个版本号收口**：建议
- V1.1.05 = 第一批（6 项，纯修 bug，不改行为）
- V1.1.06 = 第二批（假红与结果可信）
- V1.1.07 = 第三批（导入环节）
- V1.2.x = 第四批（体检/导出/上数）

这样每一版都能单独回归、单独出包，不会一次改太多导致验证不清。

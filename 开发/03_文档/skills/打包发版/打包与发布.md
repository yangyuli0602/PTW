# 打包与发布（开发用）

> 什么时候读：要出包、要让客户点「检查更新」拿到新版本时。
> 铁律：**顺序不能反**——先传包，最后写清单。反了客户会"看到新版本但下载 404"。

## 一、发版的四个动作（一条命令）

```bat
:: 1) 改版本号（只改这一个文件）
    开发\程序\app_version.py   →  APP_VERSION = "1.3.5"

:: 2) 一键发版（打包 → 推代码 → 建 Release → 传包 → 写清单）
    开发\构建\2_发版本.bat
```

不想用 bat：

```bash
开发/构建/../../tmp/buildenv/Scripts/python.exe 开发/构建/publish.py --notes "这次改了什么"
```

## 二、只想打包、不发版

```bat
:: 全量（launcher + 主程序 + zip）
..\..\tmp\buildenv\Scripts\python.exe build.py

:: 只重打主程序（改业务代码后最常用）
..\..\tmp\buildenv\Scripts\python.exe build.py --app
```

产物：`PTW.exe`（启动器）+ `runtime/`（主程序）+ `04_归档/PTW_v{ver}_win64.zip`。

## 三、发版前自检（缺一条就别发）

| 检查 | 怎么查 |
|---|---|
| 13 个测试全绿 | 见 `../测试/回归与测试.md` |
| 工作量区结构没乱 | `..\..\..\..\开发\构建\check_workspace.py`（build 会自动跑） |
| 包里没有 token | `publish.py` 会自动扫描并在命中时中止 |
| 版本号只改过一处 | `app_version.py`；`version.json` 由脚本写，别手改 |
| 客户端能更新 | 装一份旧包 → 点「检查更新 → 立即更新」→ 版本变了才算过 |

## 四、出问题怎么退

- **替换失败**：launcher 保留 `runtime_old/`，下次启动会尝试回滚；仍失败就重装 zip。
- **发错了版本**：GitHub 上删掉该 Release，再发一个更高版本号（**不要复用已发过的版本号**）。
- **同版本号重复打包**：会出现"同版本两份字节"，追溯断裂——发版前确认该版本还没发过。

## 五、几条硬约束

- 仓库必须 **public**：客户端读清单、下包都不带凭证。
- 更新只替换 `runtime/`，**永远不碰 `data/`**。
- 打包机上要停掉正在运行的 `PTWApp.exe`，否则 `runtime/` 被占用、改名失败（WinError 32）。

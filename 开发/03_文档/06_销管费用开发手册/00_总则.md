## 2. 生成顺序

**业务交付顺序（按此编号、按此推进）**：

```
BKD  →  Lead  →  TOD 及样本池  →  Cutoff 及样本池
```

**但计算依赖不是线性的**，有一条硬依赖必须承认：

```
样本池-cut off 的「是否排除」列
        └── 是 样本池-TOD 唯一的分类来源（TOD 不再维护第二套分类）
```

也就是说：**TOD 的剔除桶由 Cutoff 的判定结果直接喂**。代码里必须是先算出池子的分类，再落 TOD 页与 TOD 池；两页的呈现位置、文档编号仍按上面的业务顺序。

另外两条先后关系同样刚性：

| 前置 | 后置 | 不这样会怎样 |
|---|---|---|
| TE / SAD 写进 Lead C4/C5 | BKD 的 C22、Q 列、「进一步调查」 | C22=TE×50%=0，整张表全标「是」，等于没判 |
| BKD 合计行落定 | Lead 表1、TOD 1.1 总体 | 模板写死 E34/J205，插行后静默指错行，金额少算不报错 |

### 2.1 sheet 呈现顺序（落盘前统一排，不靠各模块抢位置）

```
1  VC&VD OAR 销售费用        ← V1.2.79 起 OAR 拆两页

规则写在 `expense.SHEET_ORDER` + `_reorder_sheets()`，在 `_append_check_sheet` 之后、`wb.save()` 之前执行一次。

- **各模块是「谁先建谁在前」**：OAR、口径Mapping 最后建就沉到底，两张池子建在 01.4 前面 —— 所以必须在最后统一重排，不能指望各模块自己挪。
- 名单里没有的 sheet（Skywind / DS_INTERNAL_* / 费用检查）保持原相对顺序排在最后。
- 排序**只动位置、不动内容**：改完 19 个 sheet 逐格比对差异必须为 0。
- 最终顺序会写进生成结果的 `sheetOrder` 字段，排查「表跑哪去了」先看这里。
- **`VC&VD.01.2 详细测试 TOD` 生成后隐藏**（`sheet_state = "hidden"`）：它只有标题和几行说明，
  真正的程序在年审 / 预审+剩余期间两页。按「详细测试 + TOD」模糊命中，不写死全名。
  隐藏只改 `sheet_state`，不影响读值、不影响跨表公式。被隐藏的表名写进 `hiddenSheets`。
  模板自带隐藏的 `SkywindSettingSheet`、`DS_INTERNAL_*` 保持原状。

## 3. 六条共性红线

1. **结转损益一律剔除，但禁止按「结转」二字整行删**。判定用「凭证内含 4103/4104 科目」或摘要精确等于/包含「结转本期损益 / 结转损益 / 期间损益结转」。`结转----确认上市费用` 是真实借方费用，删掉就少一块。
2. **本期账面数 = 借方 −（贷方 − 结转损益贷方）**。费用月末结转会把科目冲平，不还原会得到 0。
3. **TE 必须先落 Lead**，再算任何阈值（BKD C22、TOD 关键项门槛、01.4 测试门槛，全部取 TE×50%）。
4. **位置不写死**：sheet 名、表头行、合计行、页底，一律按标签文字 / 业务键现场定位。模板行号只在**肯定没被插行影响**的地方使用，且必须集中成常量并在文件里标注「改模板要同步」。
5. **期间与日期上界**：TOD 池是全量的（含日后凭证），所有 SUMIFS 必须带 `日期 <= 资产负债表日`；期间比较必须 `lpad(period,2,'0')`。
6. **不调平**：禁止 `+1`、`ROUND` 凑数、自动下「无异常」。差额必须解释；无资料留空标黄 `FFFF00`（TOD 页用 `FFF2CC` 浅黄），不填 0。

```

## 10. 界面交互契约（V1.2.70 起，与货币资金对齐）

### 10.1 账簿 → 公司：不再上传对照表

导入阶段已把主体 mapping 写进 `_books`（账簿名 → 公司全称）。`read_book_map` 的优先级：

```
本次传入 > _books（导入时的 mapping）> data/bkd_work/book_map.json（历史对照表）> tb 的 book_name/company_name
```

历史对照表只作兜底——换客户时残留的旧映射不能压过本次导入的数据。前端不再提供上传入口（接口 `/api/build/exp/map` 保留兼容）。

### 10.2 上年度费用底稿：拖拽 + 两个下拉

```
POST /api/build/exp/prior/plan   (multipart, 字段名 prior)
  → { fid, sheets:[{sheet, headerRow, rows, salesRows, adminRows, hasPrior, usable, kind}],
      recVC, recVD }
```

- `kind` 判定**按内容不按名字**：科目名称列里「销售费用」多的算 vc、「管理费用」多的算 vd、两类都有算 both
- 前端两个下拉各选一张（VC / VD），选完把 sheet 名放进生成请求的 `prior_sheets: [vcSheet, vdSheet]`
- 生成时只读这两张表回捞「上期审定数」；**口径 mapping 仍读整份文件**（缺一张会导致本年整批落「待判断」）

### 10.3 CRA：四档百分比烘进 BKD 公式

前端右栏填四档百分比 + 四项认定等级，生成请求带：

```json
"cra": {"pcts": {"Minimal":0.5,"Low":0.25,"Moderate":0.15,"High":0.1},
        "assertions": {"completeness":"Low","occurrence":"Low","measurement":"Moderate","presentation":"Minimal"}}
```

- 后端 `_fill_bkd_cra()` 按配置重写两张 BKD 的 **D8:D11**（模板原公式把百分比写死），E8 的 `=MIN($D$8:$D$11)` 不动
- 默认值 50/25/15/10（与模板一致）；**不要和货币资金的 100/75/50/25 强行统一**，两套模板本来就是两套系数
- 费用四项认定键是 `completeness/occurrence/measurement/presentation`，与货币资金的五项不同；`baseinfo.cra_of(module)` 必须按**模块**过滤，否则 occurrence/measurement 存了会被读丢
- 保存走 `/api/build/baseinfo/save`，body 只带 `{"cra":{"销管费用":{...}}}`，`_merge_cra` 按模块合并，不会清掉货币资金

### 10.4 排版

关键信息卡改两栏 `.cols2`：左＝期间/日期/客户/TE/SAD/准则/币种/预审截止月，右＝CRA 认定风险（百分比 + 四项认定）。窄屏（<1080px）自动叠回单列。

## 11. AI 通道：平台没有模型，命令负责摊平与回填（V1.2.80）

PTW 平台自身**不具备模型能力**。凡是需要"判断"的地方，一律拆成三步，不许在代码里
假装判断、也不许把判断结果硬编码：

```
①  生成时把待判断的东西摊平成 JSON（事实 + 参照系）
②  平台 AI（或人）读 JSON，给结论 + 依据 + 置信度
③  命令把结论写回该在的位置（配置 / 底稿），并保证"重新生成不会丢"
```

### 11.1 OAR 口径语义匹配（解决「上年无对应项」）

```bash
ptw.py exp … --ai-out ai_pending.json     # ① 导出：oar.items + table2.items
#    平台 AI 读 ai_pending.json，填 items[].bucket / reason / confidence
ptw.py ai-fill --file ai_result.json      # ③ 写 oar_map_ai.json（下次生成生效）
ptw.py exp …                              # 重新生成
```

- `oar.items[].ruleSuggest` 是规则建议值（仅参考），`existingBuckets` 是这家客户
  **已经用了一年的口径 + 每类 8 个典型科目名**，AI 的活儿是"映射到已有口径"，不是自由分类。
  没有参照系，同一个「技术服务费」在两家客户会被分到不同桶，跨年就不可比。
- 结果落 `口径Mapping`：**C 列＝口径、E 列＝「由AI判断」、F 列＝「依据：…；置信度 92%（高）」**。
  E 列浅绿；改 mapping 的人一眼能看出哪几行是 AI 判的、凭什么、多大把握。
- **不再出现「未匹配-待判断」**：没跑过 AI 的科目落 `规则推导-待AI复核`（黄底），
  是"先有个值、待复核"，不是"没值"。C 列永远不留空 —— 留空会让 BKD 的 XLOOKUP
  取回空白、OAR 按口径 SUMIF 静默漏计（实测漏过 76 万）。
- 跨年沿用：`oar_map_ai.json` 落在 `<data>/bkd_work/`，同一客户下年直接命中。

### 11.2 BKD 表2 变动分析

`--ai-out` 导出的 `table2.items[]` 每条形如：

```json
{"sheet":"VC.00 销售费用BKD","row":224,"nb":"NB1","bucket":"广告费",
 "now":18328933.79,"prior":8134292.36,"pct":1.2533,
 "subjects":["销售费用_宣传推广费","销售费用_展会费"],
 "evidence":[{"name":"北京视锐达科技有限公司","nature":"市场投放","amt":10908352.4,"sample":"计提-…"}]}
```

AI 只写 `text`（50~120 字，说清驱动因素、是否一次性、对认定的影响、要不要追加程序），
**金额与比例一律由公式给**，AI 不许在文字里重复数字。

回填后落两处：
- `bkd_work/table2_concl.json` —— 下次重新生成**自动带上**。不落盘的话，改个 TE
  重新生成，AI 写的整段分析就被默认描述顶掉了，项目组还以为 AI 没写。
- 直接替换 BKD 表2 每行公式的**最后一段字符串**（`_T2_TAIL`），前面 `TEXT($C224/1000,…)`
  仍然是活的引用。这是"结论可以写死、数字不能写死"的分界线。

口径一致性约束（改这块务必守住）：导出给 AI 的 `prior` 必须与表2 D 列**同源** ——
D 列是 `SUMIF(K列) = SUMIF(链接上期BKD页G列的SUMIFS)`，所以导出时也只取上期页 G 列
（按 B 列账套 + C 列科目编码对上）。曾用"解析上年底稿的上期审定数"兜底，
结果 AI 看到的上期比表上多 1,014 千，是典型的 D 类口径错位。

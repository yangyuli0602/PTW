## 一、怎么判

每条规则给三个东西：**等级 + 判定式 + 修法**。

| 等级 | 含义 | 影响 |
|---|---|---|
| **阻断** | 不过就不能合并成标准表 | 合并按钮拦住，必须改 |
| **告警** | 能合并，但底稿会缺东西或数会偏 | 页面标黄，可强行继续 |
| **记录** | 只统计，不做对错判断 | 仅进报告 |

判定式统一写成「比例 ≤ 阈值」的形式，阈值全部集中在本文件第七节，方便按客户调。

**三种状态必须分开报**，现在混着报是最大的问题：

- **本表没这一列** → 判「不适用」，不报错（例如余额表本来就没有摘要）；
- **有这一列但整列空** → 判「未映射」，报错并指向字段映射页；
- **有这一列、部分行空** → 判「填充不足」，报比例。

## 三、科目余额表 · 主体与科目（9）

| # | 字段 | 级 | 达标要求 | 不达标怎么修 |
|---|---|---|---|---|
| 1 | 公司名称 | 阻断 | ① 空值 0 行；② **一个账簿名只能对应一个公司名**，冲突 0 处；③ 与序时账的同名率 ≥ 95% | 导入「账簿→公司」对照表；或把公司名称来源设为账簿名称、某一列、文件名 |
| 2 | 账簿名称 | 阻断 | ① 空值 0 行；② 表内账簿名 ≤ 500 个（超出说明把明细列混进账簿列了） | 映射页把「账簿名称来源」设为列/工作表名/文件名/手工值 |
| 3 | 科目编码 | 阻断 | ① 空值 0 行；② **整行完全相同**（公司+账簿+编码+名称+币种+各金额+辅助核算全同）的重复行 0 处——同一科目下多个银行账户是正常的，不能只按编码判重；③ 编码里出现「合计/小计/总计/Total」等非编码值 0 行；④ 全角数字、首尾空格 0 行 | 删空行；按关键词删行（编码列，全等模式）；整行去重 |
| 4 | 科目名称 | 阻断 | ① 空值 0 行；② 「合计/小计/总计」出现在**开头或结尾**的行 0 行（夹在中间的是真科目，如「其他合计性支出」必须保留）；③ 同一编码对应多个名称 0 处 | 删小计行（用「开头或结尾」口径，不用「包含」） |
| 5 | 科目全称 | 告警 | 有这一列时填充率 ≥ 95%；同一编码对应一个全称 | 拼接「一级/二级/明细」三列生成；或改用科目名称核对（第四组会降级） |
| 6 | 一级科目 | 阻断 | ① 空值 0 行；② 纯数字占比 ≤ 10%；③ 一个一级科目只挂一个一级代码 | 定长编码用「按编码派生一级科目」（位数填 0 自动推断）；分隔符编码用「提取/生成一级科目」；缺的科目名补进 `data/std_accounts.json` |
| 7 | 科目级次 | 记录 | 有值时必须是 1–9 的整数；与「编码长度/分隔符层数」推断的级次一致率 ≥ 95%（只记录，不判失败） | 一般不用改，它只用于底稿缩进 |
| 8 | 币种 | 阻断 | ① 空值 0 行（单币种账套统一填一个值也行）；② **同公司同科目下「综合本位币」与具体币种并存 0 处**；③ 币种取值 ≤ 10 种（超出说明同一币种有多种写法，如「港币/港元/HKD」） | 按关键词删行（币种包含「综合本位币」）；币种写法用「改值·替换」统一 |
| 9 | 余额方向 | 告警 | ① 取值只能是 借 / 贷 / 平（或 D / C）；② 空值率 ≤ 5%；③ 与期末借贷列的一致性 ≥ 95%（只填了借方的行方向不应是「贷」）；④ **整表没有方向列、但有借贷分列时判「不适用」**（方向可由借贷推断） | 在映射页把「余额方向」列配上；没有这一列时留空，由期末借贷列判断方向 |

## 四、科目余额表 · 本币金额（10）

**这一组先套三条通用判定，再逐列看：**

- **可解析**：去掉千分位、括号负数后，能转成数字的行 / 非空行 = **100%**。出现 `-`、`—`、`N/A`、`无` 这类占位符 = 0 行。
- **不成负**：期末、本期、本年三类列出现负数 ≤ 10%（余额表通常存正数 + 方向；整列负数多半是本币原币配反或方向没还原）。**净额列（期初/期末余额净额）为负是正常的**（= 借 − 贷），不判。
- **不多空行**：所有金额列都为空或 0 的行 ≤ 5%（超出说明多导了汇总层、空行或表尾）。

> **v2 修正（实跑后）**：余额表的金额列天然「单边填空」——一行只在一侧有值，另一侧本来就是空。
> 所以**不逐列判空值率**，改为「按来源表判这一组有没有值」；单列只判负数与净额一致性。

| # | 字段 | 级 | 达标要求 | 不达标怎么修 |
|---|---|---|---|---|
| 10 | 期初借方（本币） | 告警 | 期初组（借方/贷方/净额任一）在该来源表有值；负数率 ≤ 10% | 映射页补列；源表确实没有期初就记录下来 |
| 11 | 期初贷方（本币） | 告警 | 同上；同一行期初借贷**同时非零** ≤ 1% | 同上 |
| 12 | 期初余额净额（本币） | 记录 | 有值时 = 期初借方 − 期初贷方（差 > 容差的行 0 行）；净额为负属正常 | 一般不用改，它是净额写法表的替代列 |
| 13 | 本期借方发生（本币） | 阻断 | 本期组在该来源表有值；负数率 ≤ 10% | 映射页补列；注意别配到「原币」列上 |
| 14 | 本期贷方发生（本币） | 阻断 | 同上 | 同上 |
| 15 | 本年累计借方（本币） | 阻断 | 本年组有值（第一组检查直接依赖这一列）；负数率 ≤ 10% | 同上；源表叫「本年累计」「累计发生额」 |
| 16 | 本年累计贷方（本币） | 阻断 | 同上 | 同上 |
| 17 | 期末借方（本币） | 阻断 | 期末组有值：借贷分列**或**净额列至少一项；负数率 ≤ 10% | 同上 |
| 18 | 期末贷方（本币） | 阻断 | 同上 | 同上 |
| 19 | 期末余额净额（本币） | 记录 | 有值时 = 期末借方 − 期末贷方（差 > 容差的行 0 行）；净额为负属正常 | 净额写法表用它代替 17/18 |

**「组级齐全性」是本组的核心新增**：现在只查「必备字段有没有映射」，没查「这一组金额整列为空」。实际最常见的事故就是期初整列配错、或本年累计没导进来，字段都在、值全是空，现在完全查不出来。
**判定要按来源表分组**——三张余额表里有的只导了本期、没导期初期末，混在一起算总账会把「某张表没这一组」误报成「数据不全」。

**再叠两条跨列判定（不绑单个字段，但必须查）：**

- **折算合理性**：同一币种下，「本币 ÷ 原币」的比值离散度 ≤ 5%。汇率在一个期间内是稳定的，比值到处乱飞 → 两列配反了。
- **汇率区间**：单一币种下，「本币 ÷ 原币」的中位数应落在 0.5–8 之间（港币≈0.92、美元≈7.2、新元≈5.4、马币≈1.7）。落到区间外 → 告警，提示"币种标错或本币原币配反"。

## 十、跨字段 / 跨表一致性（8）

这些不是单列能判的，但必须一起进「清洗达标」，否则列都合格、数还是错的。

| # | 检查 | 级 | 达标要求 |
|---|---|---|---|
| 72 | 主体名一致 | 阻断 | **只算两边都有发生额的主体**：这些主体归一后对上 ≥ 95%。余额表有、序时账没有且本年发生额为 0 的，是本期没业务的主体，不算对不上 |
| 73 | 一表一源 | 阻断 | 同一主体只从一个来源进数（跨文件重复时，只保留借贷平衡的那份） |
| 74 | 本年借贷平衡 | 阻断 | 每个主体：本年累计借方合计 = 本年累计贷方合计（容差内） |
| 75 | 余额滚动 | 告警 | 每个主体：期初 + 本期借 − 本期贷 = 期末（容差内） |
| 76 | 凭证平衡 | 阻断 | 每张凭证：借方合计 = 贷方合计 |
| 77 | 科目发生额一致 | 阻断 | 同公司同科目：余额表本期发生 vs 序时账发生，差异科目占比 ≤ 5% |
| 78 | 末级科目 | 阻断 | **按同主体**判定，父科目与明细并存 0 处（现在跨主体比前缀，会误判） |
| 79 | 期间覆盖 | 告警 | 序时账日期范围 ⊆ 余额表的会计期间范围 |

> 第 78 条现在是平台已知缺陷：判定时不区分主体，境内有 `1702`、境外有 `1702.01` 就判成父子，实测误报 3 个（按同主体重算是 0 个），而且是阻断项，只能强制合并绕过。

## 十二、怎么落地

1. **规则表化**：新增 `程序/rules/quality_rules.json`，一条一个对象：`key / target / field / level / judge / threshold / fix`。判定式用受限语法（`empty_rate`、`dup_rate`、`null_when`、`equals`），由统一引擎执行，不写散落的 SQL。
2. **页面呈现**：检查结果按「表 → 字段分类 → 字段」三层折叠，阻断项置顶；每条后面直接挂「去修」按钮，跳到对应清洗动作或映射格。
3. **兼容**：现有 `_item()` 的 `key` 全部保留，新规则挂在原有组下面，老的调用方（合并门禁 `pre_merge`）不受影响。
4. **版本**：改完是 V1.2.99，门禁行为会变严，**必须先在金斯耐那套数据上跑一遍**，确认阻断项从现在的 7 项变成多少，不能一封版就把人全拦住。

## 十三、需要你拍板的 5 处

1. **阻断项 25 条会不会太严**？我按「不过就不能合并」定的。如果实际作业中客户经常缺辅助核算、缺期初，建议把 10/11、51 里的一部分降为告警。
2. **阈值**：辅助核算 95%、日期落期间 100%、重复行 0、金额空值率 5%——这些是我按常规账套定的，你们实务上的容忍度是多少？
3. **「阶段」要不要分开**？现在是「清洗完就能达标」。实际是两段：清洗完只能保证「结构合格」，跑完五组才知道「数对不对」。建议分级成**清洗达标**与**对账达标**两个结论，不要合成一个。
4. **第 73 条「一表一源」**：重复主体只留借贷平衡那份——这条要人工确认吗？还是平台自动选？自动选的风险是万一两份都不平。
5. **要不要出 Excel 版**：79 条做成一张可勾选、可填阈值的表，方便你和客户对？

### 暴露的 2 个平台缺陷

1. **期间格式混用导致静默漏行**：明细表里「01」和「2026-01」并存时，
   期间过滤把纯月号当字符串比（`"01" < "2026-01"`），香港 3,253 行凭证凭空消失，
   组三误报 24 条「仅余额表有」。已在 `recon.py` 的 `_period_key` 补年份前缀修正。
2. **关键词删行的列名不匹配时会退化成全列搜索**（高危）：把「记账日期」写成「日期」，
   动作不报错，转而把所有列拼起来搜「2026-10」——任何列（含摘要）出现这个字样的行全被删，
   实测误删 206,244 行。**建议改成：列名找不到就报错，绝不猜。**

### 第五组「货币资金辅助核算」专项：197 → 0

第五组原先只看 `aux1/2/3`，把「账户信息在专用字段」和「第三方支付账户」两类都判成无法定位。

| 成因 | 行数 | 处理 |
|---|---|---|
| 账号映射到了 `bank_account`，没进 aux 槽 | 40 | 判定补认 `bank_account` / `bank_name`（账号本来就是账户唯一标识） |
| 账号和账户名拼在一列：`012-9006-939,宝中堂DBS账户` | 40 | 「辅助核算拆分」按逗号拆成「银行账号」「银行账户名」，分别配 bank_account / bank_name |
| 其他货币资金下的微信/支付宝/通联/京东钱包/数字人民币/富途/Pay Now | 157 | 科目名称去掉一级科目名后还有内容，就算能定位（这类账户本来没有银行账号） |
